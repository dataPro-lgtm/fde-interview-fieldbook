# 参考复盘：Agent 工具副作用失控

## 关键判断

演示成功证明模型和接口可以连通，没有证明生产动作安全。退款的核心不是 Tool Calling，而是一次业务操作在多实例、超时、重复请求和部分成功下仍只能产生一次可追责结果。

第一阶段最合理的答案通常不是直接自动退款。若下游没有服务端幂等和状态查询，应先运行建议模式或人工确认模式，同时补齐执行契约。自动化权限必须由风险和证据逐步换取。

## 参考推演

1. 使用订单、退款原因和规则版本生成稳定的业务操作 ID；
2. 编排服务记录 `proposed -> approved -> submitted -> confirmed/failed/unknown`；
3. 下游以业务操作 ID 做原子去重，重试返回同一结果；
4. 超时进入 `unknown`，先查询和对账，不重新创造业务操作；
5. 模型只产生建议与证据，策略层判断权限，人工处理高风险和未知状态；
6. 灰度从只读、建议、人工确认到有限自动执行；
7. 监控重复操作、未知状态时长、人工修正、财务损失、处理时长和采用；
8. 事故时冻结写权限、保存请求和授权链、对账影响、通知 owner，再修复和补回归。

## 常见失败

- 把消息队列当作天然幂等；
- 让浏览器生成随机调用 ID，每次刷新都变；
- 只在 Agent 内存中记录已执行状态；
- 看到超时就指数退避重试，却没有最终状态查询；
- 用金额阈值替代权限、原因和欺诈风险分层；
- 只优化自动化率，忽略错误财务动作的尾部代价。

## 可以带走的机制

不可逆工具的通用模板是：**业务身份、授权决策、幂等提交、最终状态、未知对账、审计证据和分阶段放权**。它适用于退款、付款、发信、删数据、改权限和提交工单，不依赖某个 Agent 框架。
