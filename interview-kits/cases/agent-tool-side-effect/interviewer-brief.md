# 主持人简报：Agent 工具副作用失控

## 运行流程

| 时间 | 环节 | 主持动作 |
| --- | --- | --- |
| 0—5 分钟 | 复述 | 只澄清题意 |
| 5—20 分钟 | 发现 | 对有效问题释放第一轮工作流证据 |
| 20—40 分钟 | 设计 | 追问业务身份、权限、重试和最终状态 |
| 40—55 分钟 | 事故注入 | 释放执行日志与财务影响 |
| 55—65 分钟 | 决策 | 要求给出保护、恢复和后续上线范围 |
| 65—75 分钟 | 评分 | 独立记录原话和一票否决项 |

## 证据释放

### 第一轮：候选人询问当前流程、权限或失败语义

释放 `artifacts/round-1-workflow.md`。若只问“有没有接口文档”，先追问他要验证哪个风险。

### 第二轮：候选人完成初步设计或询问生产异常

释放 `artifacts/round-2-execution-log.json`。日志显示同一业务退款因网关超时被两个应用实例执行，两次工具调用 ID 不同，但订单和金额相同。

### 第三轮：40 分钟压力注入

释放 `artifacts/round-3-pressure-injection.md`。不论候选人是否提前覆盖，都要观察其事故保护顺序。

正确方向不是背出某个消息队列，而是建立：稳定业务操作 ID、服务端幂等、执行状态查询、未知结果对账、权限与审批、证据保存和分阶段授权。

## 追问

- HTTP 超时以后，为什么不能直接再调用一次？
- 幂等键由浏览器、Agent、编排服务还是退款系统生成？为什么？
- 模型输出“应该退款”与系统有权退款之间还缺什么？
- 如果退款系统暂时不支持幂等，你怎样缩小第一阶段？
- 已经发生重复退款时，先修代码还是先保护财务影响？
- 建议模式采用率很低，是否足以成为开放自动执行的理由？
- 什么证据允许从建议、人工确认升级到有限自动执行？

## 评分

使用 [`rubric.md`](rubric.md)，再映射到总评分表。重点记录候选人是否：

- 将客户断开、调用超时、执行失败和最终未知分开；
- 给不可逆动作分配稳定身份与授权边界；
- 先停止扩大影响、保存证据和对账，再声明根因；
- 用风险分层换取工具权限，而不是一次性全量开放；
- 同时定义处理时长、人工修正、重复执行和财务损失指标。
