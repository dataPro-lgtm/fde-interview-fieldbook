# 参考复盘：多 Pod 长任务与断点续传

## 关键判断

网页连接是观察任务的订阅，不是任务本身。关闭页面只意味着消费者离开；任务是否继续、取消或暂停由任务策略决定。真正的断点续传需要可寻址任务、持久步骤状态和可重放事件。

Sticky session 只能提高“连接还在、原 Pod 还活着”时的命中率，不能作为任务可靠性边界。

## 参考推演

1. API 创建任务并返回 `job_id`，保存调用身份、输入摘要、版本和策略；
2. 队列只传递可重复领取的工作通知，数据库或工作流存储保存任务真相；
3. Worker 使用带 fencing token 的租约领取任务，旧 token 不能提交新状态；
4. 每个步骤记录 `pending/running/succeeded/failed/unknown`、输入版本和结果引用；
5. 工具调用使用稳定 operation ID，恢复先查询结果，再决定重试、补偿或人工介入；
6. 事件按任务维护单调序号，SSE 根据游标补发，客户端按事件 ID 去重；
7. token 流可以短暂缓存或分块持久化，关键步骤、工具结果和最终输出必须持久；
8. 取消是经过授权的状态转换，不等同于断开；
9. 迁移期双写事件、shadow 恢复、故障注入 Pod 驱逐和重复领取，再逐步取消粘性会话。

## 常见失败

- 只加 Redis 缓存，却不定义谁是状态真相；
- 用分布式锁但没有 fencing，旧 Worker 恢复后覆盖新结果；
- 事件日志和任务状态分别成功，无法解释缺口；
- 每个 token 都同步落库，导致成本和背压失控；
- 恢复时从最后一条文本继续，却不知道工具是否已经执行；
- 发布时让运行中任务混用新旧 prompt、模型或工具版本。

## 可以带走的机制

持久 Agent 的通用结构是：**可寻址任务、版本固定、租约单写、步骤 checkpoint、工具幂等、事件游标、授权取消和故障演练**。SSE、WebSocket 或轮询只是消费方式。
