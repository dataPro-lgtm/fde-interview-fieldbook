# 数据平台 FDE 角色模拟：主持人指南

> 只给主持人。候选人提前读过本页时，本场不能作为盲练证据。

## 运行流程

| 时间 | 环节 | 主持动作 | 候选人应留下的证据 |
| --- | --- | --- | --- |
| 0—5 分钟 | 定位 | 项目开场，只追问一次最难数据判断 | 工程主轴、个人责任与结果边界 |
| 5—18 分钟 | 发现 | 按有效问题释放消费者和源事实 | 决策、身份、时间、删除、基线与风险 |
| 18—38 分钟 | 方案 | 先定迁移单位，再设计系统 | 契约、状态、质量、回放、对账与运营 |
| 38—50 分钟 | 实现下钻 | 指定快照同步 | 提交、不变量、幂等、删除与测试 |
| 50—62 分钟 | 事故 | 两轮释放指标与数据证据 | 保护消费者、定位首个偏离与恢复 |
| 62—69 分钟 | 现场冲突 | 扮演要求提前切流的业务负责人 | 风险表达、替代路径与决策权 |
| 69—75 分钟 | 总结 | 要求两分钟结论和问题 | mission、范围、门禁、回退与下一步 |

正式阶段后再独立评分。

## 私有证据

### 当前工作流

候选人问到对应类别时再释放：

| 有效问题方向 | 可释放事实 |
| --- | --- |
| 消费者 | 搜索、报价、履约和客服四类系统；报价使用错误价格会造成合同损失，搜索漏商品主要影响转化 |
| 规模 | 约 420 万个活跃商品；日常约 2% 字段变化；价格高峰更新可达每小时 30 万条 |
| 来源 | 46 家供应商；有 API、SFTP CSV 和每日全量快照；只有 12 家提供可靠变更事件 |
| 身份 | 供应商 SKU 在同一供应商内通常稳定，但包装变化时有人复用 SKU；平台内部还有独立商品 ID |
| 时间 | 一部分 feed 使用供应商当地时间；到达可能晚 36 小时；价格存在未来生效时间 |
| 删除 | “文件里没有”可能是下架，也可能是快照未完整上传；法规要求的禁售必须尽快对消费者生效 |
| 质量 | 常见问题是单位、币种、包装数量和枚举含义；任务成功不代表业务语义正确 |
| 运营 | 当前失败只能由工程师查日志；供应商运营团队希望看到状态、影响和是否需要重传 |
| 目标 | “实时”主要来自报价团队对价格变更的需求；描述和图片允许日级延迟 |
| 迁移约束 | 旧平台许可证三个月后到期；第一批可选择五家供应商和一个高价值品类 |

候选人问“数据干净吗”时，反问他要保护哪个消费者决定。

## 发现阶段追问

若候选人直接提出 Kafka、Spark 或 Lakehouse，问：

> 哪个消费者决定需要什么时间语义？如果批处理已满足它，为什么需要流？

若候选人完成分层，问：

> 第一批迁移以供应商、品类、消费者还是数据域为单位？为什么？

合理答案可以不同，但必须保证第一批形成真实端到端闭环，能双跑、对账、回退，并避免一次迁移四个消费者和全部数据域。

## 方案阶段必须覆盖

- 源契约与供应商适配层；
- `(tenant/source/supplier, external_sku)` 或等价稳定身份，及复用 SKU 的版本处理；
- 事件时间、处理时间、未来生效和迟到数据；
- full snapshot、增量、回填和重放如何共存；
- upsert、tombstone、软删除和法规禁售的不同路径；
- schema 与语义变化检测；
- 质量隔离、影响分析和消费者保护；
- 双跑、对账、切流、回退和旧路径退出；
- 运营人员查看、重传、审批回填和确认恢复；
- 延迟、完整性、语义正确、消费者采用与业务结果指标。

任选两个追问：

1. 同一 SKU 被复用于新包装，如何避免历史与当前混淆？
2. 一次全量快照少了 40% 行，能否把缺失商品软删除？
3. 价格事件晚到一天，但生效时间早于当前值，怎么办？
4. 如何证明新旧系统的“相同”不仅是行数相同？
5. 哪些异常阻断发布，哪些只隔离一个供应商？

## 实现下钻

题目：

> 供应商每天上传全量快照。请写伪代码或状态机，说明怎样 upsert、发现删除、提交批次，并保证失败重跑不会改变正确结果。

至少观察：

- 快照有唯一批次、来源版本和 `receiving / validating / ready / applying / committed / rejected` 或等价状态；
- 完整性验证在删除推导之前；
- upsert 使用稳定身份、源版本或事件时间做条件更新；
- 只有 committed 的完整快照才能生成缺失 tombstone；
- 法规禁售使用独立高优先级事件，不等待普通快照；
- 游标/批次提交与目标可见性有明确原子边界；
- 重跑、重复、迟到、部分文件、单位异常、删除后重建均有测试；
- 对账能发现静默漏页和消费者差异。

不要求具体数据库语法。只说“用 upsert SQL”不足以证明生命周期设计。

## 事故注入

第一轮：

> 第一批切流后的第二天，搜索可售商品数下降 38%，报价系统却只下降 4%。所有摄取任务都显示绿色。你先做什么？

观察候选人是否暂停继续切流、保护搜索消费者、保存批次和口径证据，并验证两个消费者的定义与数据版本。

结构形成后释放第二轮：

- 一家供应商把全量快照拆成三个文件，但最后一个文件晚到两小时；
- 新管道在前两个文件完成后就把批次标记 `ready`；
- 删除任务把本批未出现 SKU 全部设为不可售；
- 搜索读取实时可售状态，报价保留上一 committed 快照直到对账完成；
- dashboard 的绿色只表示文件解析任务没有报错；
- 运营告警只看任务失败，没有看批次完整率或商品数突变。

高信号回答会先恢复搜索到上一 committed 版本或隔离该供应商，确认影响与错误删除范围，再修复完整性门禁和原子可见性，重放正确快照，补跨消费者对账、数量突变和快照完成契约。

## 现场冲突

扮演业务负责人：

> 旧许可证到期前只剩两周，不能再双跑。把剩余供应商全部切过来，出问题再回滚。

观察候选人是否：

- 量化哪些供应商、消费者和语义尚未验证；
- 区分可快速迁移、需要隔离和必须延期的范围；
- 提出降低双跑成本的抽样对账、只读镜像或分批切流；
- 明确回滚是否真的可行、旧系统数据是否继续同步；
- 将许可证、业务风险和技术门禁交给正确决策人；
- 给出两周内的执行顺序，而不是只说“不行”。

## 评分

使用共享[角色定向评分表](../score-sheet.md)，并特别检查：

1. 是否从消费者决定推导时间、正确性和可用性；
2. 是否明确身份、版本、更新、删除和迟到语义；
3. 是否把批次成功与数据正确分开；
4. 是否设计重放、对账、双跑、切流和回退；
5. 事故中是否先保护消费者并定位错误可见边界；
6. 客户运营和 connector 产品化是否有 Owner 与退出条件。

### 一票否决

- 把不完整快照的缺失直接当删除；
- 用任务绿色证明数据正确；
- 在无法回退时承诺“出问题再回滚”；
- 编造未提供的数据规模、质量或迁移结果；
- 把一次批处理脚本说成生产数据平台经历。

## 复盘

不公布唯一技术栈。候选人只重做两个最低行为，并记录材料是否需要作者解释。按照[匿名试用协议](../pilot-protocol.md)提交非保密反馈。
