# AI / Agent FDE 岗位作战包

> **适合目标：** 生产 LLM 应用、Agent 工作流、模型平台或 AI 转型方向的 FDE<br>
> **训练时间：** 十次有输出的练习，而不是十天阅读<br>
> **完成标准：** 能证明自己会选择工作流、控制不确定性、亲手交付并对采用负责

## 1. 先纠正一个误区

AI / Agent FDE 不是“比应用工程师更会讲客户故事”，也不是“会用更多 Agent 框架”。公开岗位信号反复指向一条更完整的责任链：理解客户日常工作，判断 AI 是否值得使用，亲手建立生产系统，用评测和真实采用验证效果，再把现场失败反馈给产品。

截至 2026-08-21，本角色包使用以下一手信号：OpenAI FDE 岗位把 discovery、scoping、build、rollout、adoption 和 eval-driven feedback 放在同一责任链；Anthropic 岗位公开提到 MCP server、sub-agent、Agent Skill 与生产评测；Vercel 将 AI 工作流选择、生产 Agent、MCP、客户代码和知识转移并列；Diligent 强调 golden dataset、regression、tracing、guardrail，以及先判断工作流是否需要 Agent。来源 ID 和范围见 [`data/role-playbooks.json`](../../data/role-playbooks.json)。

这些信号说明能力的重要性，不证明任何公司的具体面试轮次。

## 2. 面试官需要消除的五个风险

| 风险 | 低信号表现 | 需要看到的证据 |
| --- | --- | --- |
| 技术先于问题 | 一听到需求就设计 Agent | 能比较规则、检索、单次生成、工作流与 Agent，并说明不用 Agent 的条件 |
| Demo 代替生产 | 只展示一次成功对话 | 离线评测、线上观测、失败分桶、灰度、回退和人工接管 |
| 框架代替工程 | 反复列 LangGraph、MCP、Skill | 工具契约、权限、幂等、超时、重试、状态和副作用控制 |
| 模型指标代替价值 | 只谈准确率和 benchmark | 用户动作、处理时间、采用、人工修正和高风险错误 |
| 一次性交付 | 每个客户重做 prompt 和 connector | 能识别共同核心、变化维度和产品反馈去向 |

你的准备应该围绕消除这些风险，而不是继续扩充 Agent 名词表。

## 3. 六条核心证据

### 证据一：你会判断是否该用 AI

准备一个你主动缩小或拒绝 AI 范围的故事。说明当前流程、决策点、错误代价、可接受延迟、规则覆盖率和人工能力。给出至少两个备选方案，并解释为什么最终选择的自动化程度与证据匹配。

追问边界：如果只能说“业务很复杂，所以用大模型”，证据不成立。

### 证据二：你做过端到端最小闭环

展示真实输入如何进入系统，模型如何获得上下文，工具如何执行，结果如何到达用户动作，以及日志和反馈如何回来。最小闭环不是最小 UI，而是最小可验证责任链。

可展示材料：架构图、接口契约、测试、trace、评测样本、发布记录或匿名化复盘。

### 证据三：你能分层诊断失败

准备一次失败，不要只讲“换模型后好了”。至少区分：输入或数据没到、权限过滤错误、检索失败、上下文构造失败、模型决策错误、工具执行失败、输出正确但用户未采用。说明你怎样固定请求、数据、代码、prompt、模型和工具版本，再定位第一处偏离。

### 证据四：你控制了工具副作用

选一个写操作或外部动作，说明身份如何传递、权限在哪里判定、重复调用如何去重、超时后如何确认结果、失败如何补偿、哪些动作必须预览或审批、审计日志记录什么。

只讨论 tool schema，不讨论副作用，通常不足以证明生产 Agent 能力。

### 证据五：你让用户真的采用

准备一个“技术正确但用户不用”的案例。说明用户为什么绕过系统，是信任、速度、解释、流程切换、责任还是激励问题；你如何通过 shadow、建议模式、人工复核或局部自动化改变采用，而不是只培训用户。

### 证据六：你把现场学习沉淀成杠杆

说明一个现场问题怎样进入了 reusable eval、connector、policy、skill、workflow template、平台能力或产品路线。必须同时讲清什么被抽象、什么保留配置、谁维护，以及第二个场景是否验证了复用价值。

## 4. 把证据路由到可能的面试面

| 可能的观察方式 | 重点准备 | 主动暴露的边界 |
| --- | --- | --- |
| 项目深挖 | 从工作流选择到上线采用的一条完整链 | 团队贡献与个人贡献；仍未解决的问题 |
| 编码或调试 | API、数据处理、状态、测试、错误恢复 | 不熟悉的框架可以查，核心语言和调试不能外包 |
| AI 系统设计 | 数据流、控制流、证据流、评测、人工接管 | 为什么不是全自动；哪些高风险动作不开放 |
| 客户角色扮演 | 先问工作流和风险，再承诺范围 | 不能承诺零幻觉或两周全面替代人工 |
| 事故场景 | 保护、复现、分层归因、回滚、回归 | 不用“模型不稳定”概括所有根因 |
| 产品反馈 | 共性、变化维度、维护归属和复用验证 | 不是所有定制都值得产品化 |

## 5. 三个必做练习

### 练习 A：为什么不用 Agent

场景：客服团队希望“做一个能自主处理全部工单的 Agent”。

在 20 分钟内给出：

1. 当前工作流与工单风险分层；
2. 规则、检索辅助、建议生成、受控工作流和自主 Agent 五种方案比较；
3. 第一阶段只自动化哪一个决策点；
4. 人工接管与停止条件；
5. 证明价值需要的业务指标和安全指标。

评分重点：能否把“自主程度”当成需要证据换取的权限，而不是产品卖点。

### 练习 B：有副作用的工具执行器

使用熟悉的语言实现一个最小工具执行器，支持：

- 明确的输入校验与调用身份；
- idempotency key；
- 超时、重试和最终状态查询；
- dry-run 或 preview；
- 审批门槛；
- 结构化审计记录；
- 单元测试覆盖重复请求、超时后成功和权限拒绝。

不要求接入真实外部系统，可以使用内存或合成接口。评分看工程边界，不看框架数量。

### 练习 C：准确率突然下降

场景：意图识别准确率从 90% 降到 28%，最近同时发生了数据更新、prompt 调整和工具升级。

你需要画出版本矩阵，固定请求回放，区分数据漂移、标签口径、prompt 路由、模型版本、工具结果和观测计算问题；先保护高风险流量，再用一次只改一个变量的实验定位首个偏离层。最后新增回归样本和发布门禁。

评分重点：不是能列多少原因，而是能否建立可证伪的排查顺序。

## 6. 十次训练顺序

| 次数 | 训练 | 必须留下的产物 |
| ---: | --- | --- |
| 1 | 90 秒定位 | 一版录像与三处空泛句 |
| 2 | 最强 AI 项目深挖 | 个人决策、产物、结果和边界表 |
| 3 | “为什么不用 Agent” | 五方案比较与 thin slice |
| 4 | 工具执行器编码 | 可运行代码、测试和失败说明 |
| 5 | 工作流优先系统设计 | 数据流、控制流、证据流 |
| 6 | 评测与发布 | 黄金集分桶、门禁、灰度和回退 |
| 7 | 客户压力角色扮演 | 拒绝、替代路径、下一步录像 |
| 8 | 准确率事故 | 固定版本的 TRACE 复盘 |
| 9 | [角色定向盲练](../mock-loops/role-targeted/ai-agent-fde/candidate-brief.md) | 独立评分和两项最大风险 |
| 10 | 只重练两项风险 | 第二版录像与盲评分差异 |

练习材料优先使用：[生产事故案例](../cases/production-incident/README.md)、[受监管 Agent 案例](../cases/air-gapped-ai-deployment/README.md)、[90 分钟 AI FDE 模拟](../mock-loops/ai-fde-90-minute.md)。

## 7. 作品集应该证明什么

一个可信的 AI FDE 作品，不需要做成大而全的平台，但至少应回答：

- 用户在什么工作流里做什么决定；
- 为什么选择当前自动化程度；
- 数据、prompt、模型、工具和策略如何版本化；
- 离线评测如何分桶，线上如何观察用户动作；
- 权限、人工接管和工具副作用如何控制；
- 如何灰度、回退和处理长任务恢复；
- 哪部分可复用，哪部分明确保持客户配置。

如果仓库只有界面截图、模型调用和一条 happy path，它证明的是原型能力，不是生产 FDE 能力。

## 8. 就绪门槛

你不需要满足所有偏好项，但进入面试前应该能做到：

- 说出一个不用 Agent 的合理场景；
- 画出一次请求的数据流、控制流和证据流；
- 对一个有副作用工具解释权限、幂等、重试和审计；
- 用分层样本而不是总准确率设计 eval；
- 解释一次灰度、回退或人工接管的真实判断；
- 区分直接生产经验、相邻经验与设计练习；
- 将至少一个现场失败连接到可复用产品能力。

任何一项只能用术语回答，就把它列为下一次训练，而不是继续修改简历措辞。
