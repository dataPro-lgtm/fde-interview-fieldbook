# 数据平台 FDE 岗位作战包

> **适合目标：** 数据基础设施、数据产品、模型数据供应链或企业数据集成方向的 FDE<br>
> **训练时间：** 十次有输出的练习<br>
> **完成标准：** 能把客户数据从“接进来”做到可运营、可恢复、可解释地进入业务结果

## 1. 数据 FDE 不是“驻场数据工程师”

数据平台型岗位当然看 SQL、Python、分布式处理、建模和云基础设施，但只证明管道能跑还不够。FDE 要把数据工程放进客户现场：源系统为何变化、谁消费数据、错误何时被发现、运营人员如何处理异常、回填如何影响下游、客户团队如何接手，以及重复需求如何回到平台能力。

截至 2026-08-21，Scale AI 的官方岗位页强调高质量数据基础设施、客户和运营人员使用的系统、低周转时间、全栈交付、大规模处理与快速实验；OpenAI FDE 岗位把发现、构建、上线、采用和现场反馈连接为端到端责任。它们支持本角色包的能力方向，但不代表所有数据 FDE 岗位具有相同技术栈或面试流程。

## 2. 面试官需要消除的五个风险

| 风险 | 低信号表现 | 需要看到的证据 |
| --- | --- | --- |
| 组件清单代替设计 | 先说 Kafka、Spark、Lakehouse | 从消费者、数据语义、变化率、延迟和错误代价推导架构 |
| 一次导入代替同步 | 只讲全量 ETL | 增量游标、幂等、upsert、删除、回填和 schema evolution |
| 数据质量停在规则 | 列非空、唯一性、范围检查 | 质量所有权、隔离、重放、影响面和下游决策保护 |
| 后端管道忽略运营 | 只有 DAG，没有人如何处理失败 | 状态、告警、重试、人工修复、审计和客户可见性 |
| 客户定制无法复用 | 每个 connector 单独维护 | 契约核心、适配层、配置边界和升级策略 |

## 3. 六条核心证据

### 证据一：你定义过数据契约

准备一个接口不是由你完全控制的案例。说明源数据的主键、事件时间、更新语义、删除语义、必填字段、枚举、时区、schema 变化和迟到数据如何约定。讲清楚契约失败时是拒绝、隔离、降级还是接受并标记。

“我们和上游对齐了格式”不是充分证据；契约必须能进入测试、监控和责任分配。

### 证据二：你做过可恢复同步

展示一次全量、增量、回填和重放如何共存。至少解释：游标推进的原子性、重复消息、乱序、断点续跑、幂等键、doc_id 或业务主键、upsert、软删除与物理删除边界，以及失败后怎样证明没有静默丢数。

### 证据三：你处理过 schema 与语义变化

字段增加不等于安全，字段含义、单位、枚举和去重逻辑变化更危险。准备一个变化案例，说明如何发现、评估影响、双读或兼容、回填、通知下游并退出旧版本。

### 证据四：你建立过质量闭环

除了规则，说明数据质量事件怎样关联到来源、批次、租户和消费者；怎样判断阻断发布还是局部降级；如何保留坏数据证据；修复后怎样重放；哪些指标反映数据正确，哪些指标只反映任务成功。

### 证据五：你为运营人员设计过系统

数据平台不是只有工程师使用。展示运营或客户团队如何查看同步状态、理解失败、发起重试、审批回填、查看影响和确认恢复。若只能通过开发者登录机器手工改状态，交接风险仍然很高。

### 证据六：你把 connector 经验沉淀为平台能力

说明协议、认证、映射、速率限制、游标、删除、重试和观测中，哪些属于通用 connector contract，哪些属于源系统适配。给出版本、兼容和退出策略，避免把复制代码误称为平台化。

## 4. 一个生产级同步问题怎么回答

题目：知识库每天变化，`doc_id` upsert 和软删除的边界是什么？

强回答不会从 SQL 语句开始，而会先确认身份和生命周期：

1. `doc_id` 是源系统稳定 ID、业务复合键，还是内容 hash；
2. 同一文档修订是否保持身份，权限变化是否独立版本化；
3. 删除是用户撤回、权限不可见、源端不存在，还是保留期到期；
4. 下游检索、引用、缓存和评测何时不再看到旧内容；
5. 是否需要审计、恢复和法律保留。

一种常见设计是以 `(tenant_id, source_id, external_doc_id)` 作为稳定身份，内容和权限分别带版本；upsert 只有在源版本或内容摘要变化时生成新版本，并保证索引更新幂等。软删除立即从在线检索和生成路径排除，同时保留删除原因、源版本、时间和审计信息；经过保留期、确认没有法律保留且下游清理完成后，再物理删除。

这不是通用答案。若源系统提供可靠 tombstone，可以事件驱动；若只能做周期快照，就需要连续多次缺失、快照完成标志或对账机制，不能把一次未抓到当删除。权限撤销通常也不应等待普通内容删除流程，因为它是访问控制事件。

## 5. 把证据路由到可能的面试面

| 可能的观察方式 | 重点准备 | 主动暴露的边界 |
| --- | --- | --- |
| SQL / Python 编码 | 正确性、边界、测试、复杂度和可读性 | 数据规模与内存假设；不能只写 happy path |
| 数据系统设计 | 契约、状态、吞吐、延迟、一致性、回放 | 哪些是一致性要求，哪些只是方便选择 |
| 调试场景 | 固定批次、版本和消费者，定位第一处偏离 | 任务成功不代表数据正确 |
| 客户发现 | 从报表或模型问题追到业务决策与源语义 | 不把所有数据问题归咎于上游脏数据 |
| 项目深挖 | 个人取舍、迁移、事故和运营交接 | 团队平台能力与个人贡献分开 |
| 产品反馈 | connector contract 与源特定适配 | 抽象成本可能高于下一次复用收益 |

## 6. 三个必做练习

### 练习 A：增量同步与删除

实现一个依赖最少的同步程序，输入两次源快照或事件流，输出版本化目标表。至少覆盖：

- 稳定业务身份与租户隔离；
- 重复、乱序和迟到更新；
- 游标或批次提交；
- upsert 与 tombstone；
- 软删除后在线不可见；
- 失败重跑结果一致；
- 对账报告与异常隔离。

测试必须包含源端重复、一次快照不完整、权限撤回和删除后重建。

### 练习 B：数据平台迁移

使用[数据平台迁移案例](../cases/data-platform-migration/README.md)，在不提前看面试官材料的情况下完成：现状工作流、迁移单位、双跑、对账、回填、切流、回退和交接。要求同时解释技术迁移与用户迁移，不能把“任务跑完”当作完成。

### 练习 C：指标突然变化

场景：一个核心指标一夜下降 60%，管道全部显示成功。依次检查口径版本、源系统变化、事件时间、迟到、去重、关联覆盖、权限过滤、消费者查询和仪表盘缓存。先保护业务决策，再确定首个偏离层，最后建立能在任务成功时仍发现语义错误的监控。

## 7. 十次训练顺序

| 次数 | 训练 | 必须留下的产物 |
| ---: | --- | --- |
| 1 | 90 秒岗位定位 | 数据主轴、客户结果和产品反馈 |
| 2 | 最强数据项目深挖 | 契约、规模、个人取舍、事故与结果 |
| 3 | SQL / Python 限时实现 | 正确解、测试和复杂度说明 |
| 4 | 增量同步练习 | 可重跑实现和对账报告 |
| 5 | 数据系统设计 | 数据流、状态机、质量和回放 |
| 6 | 迁移案例第一轮 | 决策日志与未验证假设 |
| 7 | 语义事故排查 | 版本矩阵和首个偏离层 |
| 8 | 客户压力场景 | 对不现实时间表的替代方案 |
| 9 | [角色定向盲练](../mock-loops/role-targeted/data-platform-fde/candidate-brief.md) | 独立评分和两个否决风险 |
| 10 | 定点重练 | 第二版实现或回答与盲评分差异 |

## 8. 作品集应该证明什么

一个可信的数据平台 FDE 作品应同时包含工程和运营两条路径：

- 源契约、稳定身份与 schema 变化策略；
- 增量、回填、删除、幂等和断点续跑；
- 数据质量隔离、对账和影响分析；
- 客户或运营人员如何查看、重试和恢复；
- 消费者如何安全迁移，如何双跑和回退；
- 监控如何覆盖语义正确性，而不仅是任务状态；
- 哪些 connector 机制可复用，哪些保持源特定配置。

如果项目只展示一个批处理脚本和最终表，它可以证明编码能力，但不足以证明生产交付和客户运营能力。

## 9. 就绪门槛

- 能清楚解释一次数据身份、更新和删除语义；
- 能实现并测试一个可重跑增量同步；
- 能区分 schema 兼容与语义兼容；
- 能设计双跑、对账、切流和回退；
- 能从“指标错了”定位到版本化证据，而不是只查 DAG；
- 能展示客户或运营团队如何独立恢复；
- 能说明一次定制为何进入或没有进入平台能力。
