# 完整示例：把一条合成 AI FDE JD 变成训练计划

> 本页的公司、岗位和候选人均为虚构，所有数据都是教学用合成信息。它展示拆解方法，不影射任何真实公司的面试题、流程或候选人经历。

## 1. 合成岗位

**岗位：** Enterprise AI Forward Deployed Engineer

公开说明摘要：

> 与企业客户共同识别高价值工作流，设计并构建生产级 AI 应用；把内部数据和工具接入 Agent；通过评测、观测和人工反馈持续提高可靠性；推动用户采用；把重复交付模式反馈给产品团队。要求 Python 或 TypeScript 生产经验，能够进入客户环境工作。具有受监管行业或 MCP 经验者优先。

这段话不是待背诵的技能列表。先把它分为事实信号。

## 2. 一页岗位简报

### 公开事实

| 类别 | 可观察内容 |
| --- | --- |
| 客户结果 | 识别高价值工作流、推动用户采用 |
| 工程主轴 | 生产 AI 应用、内部数据与工具集成 |
| 生产责任 | 评测、观测、人工反馈、可靠性 |
| 现场方式 | 进入客户环境、与客户共同构建 |
| 产品杠杆 | 将重复模式反馈给产品 |
| 明确门槛 | Python 或 TypeScript 生产经验 |
| 偏好信号 | 受监管行业或 MCP |

### 训练假设

- 项目深挖可能重点追问从发现到采用，而不只问模型实现；
- 编码可能偏 API、数据或调试，但形式未知；
- 系统设计可能要求处理工具副作用、评测和人工接管；
- 客户场景可能观察范围控制和对不现实要求的回应；
- MCP 是偏好信号，不应挤占生产工程基本功训练。

### 向招聘方确认

1. 编码更偏算法、实际应用，还是已有代码调试？
2. 系统设计是否包含 AI/数据场景？
3. 客户案例只观察 discovery，还是需要给出技术方案？
4. 可以使用文档或编码助手吗？
5. “进入客户环境”对应的出差或现场频率是什么？

## 3. 合成候选人

候选人“小林”有四年数据与后端经验，主要使用 Python。他负责过企业知识同步、权限过滤、API 和监控；做过一个内部 RAG 原型，但没有把自主 Agent 上到生产，也没有正式使用 MCP。

这个背景不是“差一点什么都满足”，而是一组需要诚实分级的证据。

## 4. 证据矩阵

| 岗位信号 | 等级 | 当前证据 | 追问风险 | 下一步 |
| --- | :---: | --- | --- | --- |
| 识别高价值工作流 | A | 曾和客服团队梳理知识更新与工单升级流程 | 过去主要从数据需求进入，业务基线不完整 | 补一张当前工作流和决策点 |
| Python 生产交付 | D | 负责同步服务、API、测试、监控与值班 | 要说清个人代码和规模，不使用“我们都做了” | 整理提交、测试和匿名化事故证据 |
| 内部数据与工具集成 | D | 做过租户隔离、权限过滤和外部 API | 工具调用副作用和审批经验较弱 | 实现一个可审计工具执行器 |
| AI 评测与可靠性 | A | 做过检索评测和线上失败分桶 | 没有 Agent 轨迹与工具回归 | 用合成 Agent 场景扩展黄金集 |
| 生产 Agent | E | 只有设计练习，没有生产责任 | 若说成经验会在追问中失去信任 | 明确称为设计练习，重点展示机制 |
| MCP | G | 读过协议，没有可展示实现 | 容易陷入协议背诵 | 完成最小 server，并解释授权边界 |
| 用户采用 | A | 处理过客服绕过知识系统的问题 | 缺少采用前后指标 | 回到记录中恢复真实基线或承认缺失 |
| 产品反馈 | A | 将两类源适配抽成 connector contract | 尚未证明第二个团队复用 | 准备失败边界，不夸大平台化 |

`D/A/E/G` 分别代表直接证据、相邻证据、设计练习和真实缺口。

## 5. 两个真正的否决风险

小林最容易犯的错误不是不会 MCP，而是：

1. 把数据同步项目讲成后端实现，无法证明自己理解并改变了客户工作流；
2. 为了匹配岗位，把 RAG 原型和 Agent 设计练习包装成生产 Agent 经验。

因此训练不应平均分给八行能力。前五次重点修第一个风险，所有回答都明确证据等级来控制第二个风险。MCP 只安排一次最小实现，避免追热点挤占主线。

## 6. 项目故事如何重构

### 原始讲法

> 我们做了一个企业知识库。我负责 Python 后端，用定时任务同步文档，做向量检索和权限过滤，最后准确率提高了。

问题：用户和工作流不见了；“我们”和个人贡献混在一起；准确率没有定义；上线、采用和失败边界缺失。

### 第一版证据化讲法

> 客服团队每天处理约几百条内部工单，但知识更新后经常要等人工通知，旧答案仍会被引用。我负责把三个源系统的更新、权限和删除语义统一进同步服务，并把检索结果限制在调用者可访问范围。第一阶段没有做自主回答，只在工单编辑器里提供带引用的建议，因为错误回复仍需客服承担责任。
>
> 我设计了稳定文档身份、增量游标、软删除和对账报告，也建立了按来源与权限场景分桶的检索回归。上线先 shadow，再开放给一组客服。我们发现主要问题不是召回，而是更新状态不可见导致客服不信任；增加同步状态和失败解释后，试点组使用率才稳定上升。这里的数据同步和权限服务是我直接负责的，客服界面由另一位工程师实现。我们没有部署自主 Agent，工具执行和人工审批是我现在通过设计练习补的能力。

这版仍需用真实、可披露的基线和结果替换模糊数量。若原记录无法恢复，就应直接说测量缺口以及后来如何补监控，不能编造数字。

## 7. 十次训练计划

| 次数 | 任务 | 评分证据 | 通过条件 |
| ---: | --- | --- | --- |
| 1 | 录制 90 秒定位 | 是否先讲工程主轴和客户结果 | 无“热爱 AI”式空话，证据等级清楚 |
| 2 | 画知识更新工作流 | 用户、决策、失败成本、基线 | 不从组件图开始 |
| 3 | 做 10 分钟项目深挖 | 个人决策、产物、结果、边界 | 能承受三轮“为什么”追问 |
| 4 | 实现工具执行器 | 权限、幂等、超时、审批、测试 | 重复与超时路径可验证 |
| 5 | 做不用 Agent 的方案比较 | 五种自动化程度 | 自主程度由风险与证据推导 |
| 6 | 设计生产 AI 工作流 | 数据流、控制流、证据流 | 含 eval、灰度、回退和人工接管 |
| 7 | 完成最小 MCP 练习 | 工具契约与授权边界 | 不把协议实现当业务价值 |
| 8 | 做客户压力角色扮演 | 拒绝、替代方案、下一步 | 不承诺两周全自动 |
| 9 | 完成 90 分钟模拟 | 总评分表和追问记录 | 找出两个行为问题，不补新题库 |
| 10 | 重录最低分片段 | 第一版与第二版盲评 | 至少一个行为锚点提升一级 |

## 8. 简历不是复制 JD

小林可以写：

> 负责多租户企业知识同步服务，统一增量游标、版本、权限与软删除语义；建立分来源和权限场景的检索回归与对账，支持试点团队从 shadow 进入带引用建议模式。

但不能写：

> 主导生产级 Agent 平台与 MCP 生态建设，显著提升企业智能化水平。

后一句包含未经证实的生产 Agent、平台、生态和业务结果。关键词更匹配，可信度却更低。

## 9. 最终面试开场

> 我最强的工程主轴是 Python 后端和持续变化的企业数据。我过去负责过多源知识同步、租户权限、检索回归和上线观测，也经历过技术结果正确但客服不愿采用的阶段。这让我形成的判断是：企业 AI 的难点不只是模型，而是数据变化、权限、用户责任和发布证据必须连成闭环。我没有把自主 Agent 上过生产，所以不会把设计练习说成实战；但工具状态、幂等、审批和可恢复工作流与我原来的生产责任高度相邻。我应聘 AI FDE，是希望把这条工程主轴延伸到完整的客户发现、AI 工作流与产品反馈。

这段话不是模板答案。它有效的前提，是后续每句话都有项目材料和边界支撑。

## 10. 示例教会我们的事

- 岗位定向不是把所有词贴到简历上，而是选择最强证据主线；
- 相邻经验可以有价值，前提是明确哪些机制可迁移、哪些仍需学习；
- 训练计划围绕否决风险，而不是围绕章节目录；
- 缺少真实结果时，补测量或承认缺口，不能用“显著提升”填空；
- 招聘流程是待确认假设，公开 JD 只支持能力方向。
