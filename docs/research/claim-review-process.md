# 争议事实评审流程

公开指南最危险的错误，不是少写一个热点，而是把范围有限的证据写成普遍事实。这个流程用于处理岗位要求、地区差异、协议状态、安全建议、翻译含义和生产判断上的争议。

## 1. 什么问题应该进入争议评审

- 一条结论没有来源，或来源无法直接支持它；
- 官方来源与当前正文冲突；
- 两个可信来源给出不同版本、团队或地区口径；
- 社区经验被写成公司政策；
- 翻译提高或降低了原文的确定性；
- 一项建议在特定行业、规模或风险条件下可能有害；
- 来源页面下线，正文仍使用“当前”措辞。

单纯偏好不同不需要评审。例如更喜欢某个框架，不能自动推翻一个说明了约束与边界的方案。

## 2. 提交最小证据包

使用 [Claim dispute Issue](https://github.com/dataPro-lgtm/fde-interview-fieldbook/issues/new?template=claim-dispute.yml)，至少提供：

1. 争议句子及文件位置；
2. 你认为它声称了什么；
3. 直接来源、核验日期和证据等级；
4. 来源能支持的最窄结论；
5. 适用团队、版本、地区、时间和例外；
6. 建议处理：保留、缩窄、分拆、降级、删除或标记未决。

不要粘贴整份招聘页面或受版权保护材料。引用短片段时只保留判断所必需的部分。

## 3. 评审顺序

### 第一步：冻结争议对象

先固定文件、段落和当前 commit。否则讨论期间正文继续变化，参与者会争论不同版本。

### 第二步：把事实、解释和建议拆开

“岗位写了 MCP”是事实；“MCP 已成为所有 FDE 必备”是解释；“候选人应该实现一个 MCP server”是建议。三者需要不同强度的证据，不能用第一层直接跳到第三层。

### 第三步：检查证据权限

优先使用雇主、规范维护者、标准组织和项目官方资料。多个独立来源可以支持常见模式，但数量不能补救来源本身与结论无关。社区经历可以说明实践摩擦，不能宣布公司政策。

### 第四步：寻找能同时容纳冲突的边界

很多冲突实际来自团队、级别、版本或地区不同。优先写成“在什么条件下 A 成立，在什么条件下 B 成立”，不要为了得到一句整齐结论而抹掉差异。

### 第五步：记录决定和反证条件

重大修改进入 `CHANGELOG.md`；时效性来源进入 `data/sources.json`。如果保持未决，要写清缺少什么证据、下一次在何时复核，而不是留一句模糊的“有争议”。

## 4. 可能的评审结果

| 结果 | 何时使用 | 正文动作 |
| --- | --- | --- |
| 接受 | 新证据直接支持更准确结论 | 修改正文、来源和变更记录 |
| 缩窄 | 原结论方向合理但范围过大 | 加团队、地区、版本或时间边界 |
| 分拆 | 两种说法在不同条件下都成立 | 写成条件分支，不强行二选一 |
| 降级 | 只有社区经验或间接证据 | 明确标为 Community，不写成官方事实 |
| 未决 | 证据真实冲突且无法消解 | 保留冲突、所缺证据和复核点 |
| 驳回 | 来源无关、不可验证或违反内容政策 | 在 Issue 说明理由，不进入正文 |

## 5. 谁说了算

这不是多数投票，也不是维护者凭资历拍板。决定应以证据与结论的匹配度为核心：来源是否直接、是否当期、是否覆盖所述范围、是否存在反例、措辞是否保留不确定性。维护者负责合并和记录，不拥有把个人经验升级成事实的特权。

评审没有固定响应时限承诺。未处理 Issue 会公开保留；高风险安全错误、明显失效来源和可能误导求职者的确定性陈述优先。

## 6. 隐私和公平边界

不得为了证明观点上传真实候选人信息、客户资料、内部招聘文档、泄露题目或付费内容。涉及地区时，只讨论公开岗位要求和交付条件，不推断受保护身份、签证结果、族群能力或私人招聘策略。

证据等级、时效和引用规则见[来源与时效政策](source-policy.md)。
