# v0.6 到 v1.0 版本执行计划

> **目的：** 把 Fieldbook 从内容完整的面试资料，推进为读者能够独立训练、主持人能够独立运行、维护者能够持续验证的成熟项目。<br>
> **基线：** `v0.5` 已提供岗位定向方法、三类角色包和角色盲练，但真实求职者效果尚未验证。<br>
> **原则：** 自动化通过不等于学员有效，合成案例不等于生产经历，独立评审未发生就不得标记为完成。

## 1. 为什么不能直接把版本号改成 1.0

仓库已经具备较强的内容密度和工程检查，但成熟版本还需要回答五个不同问题：

1. 读者是否知道下一步具体做什么；
2. 案例能否覆盖 FDE 常见的生产责任，而不是只覆盖架构表达；
3. 不同评审者是否能依据相同证据给出接近的判断；
4. 中英文入口是否指向同一套核心能力和完成标准；
5. 发布结论能否由版本化证据重现，而不是依赖作者记忆。

因此 v0.6—v1.0 每一版只解决一类主要风险，并保留可以单独回归的契约。

## 2. 版本主线

| 版本 | 主要风险 | 核心交付 | 自动化门禁 | 外部门禁 |
| --- | --- | --- | --- | --- |
| v0.6 | 读者看得懂但练不起来 | 7/14/30 天路径、训练日志、完成证据 | 路径连续、文件存在、完成规则充分 | 读者无需作者解释即可完成 |
| v0.7 | 案例数量与生产风险覆盖不足 | 十套完整 Field Case Lab | 文件契约、剧透隔离、风险元数据、合成数据卫生 | 非作者主持并记录阻塞点 |
| v0.8 | 评分依赖评审者个人感觉 | 评分锚点、盲评与裁决协议 | 校准场景、锚点引用、评分完整性 | 两位评审独立评分并分析分歧 |
| v0.9 | 双语路径和年度证据不对齐 | 核心双语对照、来源归档、发布清单 | 对照覆盖、链接、归档摘要和完整性 | 双语读者可独立找到等价训练路径 |
| v1.0 | 无法证明发布物整体可重现 | 版本化发布候选与全量验收记录 | 全部 CI、发布清单、干净构建 | 所有必须的人类验证门禁有真实证据 |

## 3. 每一版的完成定义

每一版必须同时具备：

- **用户入口：** README 或学习地图能解释谁应该使用；
- **核心资产：** 不是只有说明，而是能产生学员产物的练习；
- **机器契约：** 新增结构由数据清单和校验器约束；
- **边界测试：** 至少覆盖缺文件、重复 ID、错误顺序或证据不足；
- **维护说明：** 贡献者知道何时更新、怎样降级结论；
- **验收记录：** 分开记录自动化通过、人工审阅和未验证事项；
- **变更记录：** README、Roadmap、Changelog 和导航一致。

单纯新增篇章、把待办框勾上，或者只在作者机器上打开成功，都不算完成。

## 4. 证据等级

后续版本统一使用四级发布证据：

| 等级 | 含义 | 可以声称什么 | 不可以声称什么 |
| --- | --- | --- | --- |
| A0 | 文件存在、人工自查 | 草稿已形成 | 可运行、可复用 |
| A1 | 自动化契约与回归通过 | 结构完整、引用有效、规则被机器检查 | 学员有效、评分稳定 |
| H1 | 非作者按协议完成一次 | 可以独立运行一次 | 对不同背景普遍有效 |
| H2 | 多背景重复运行并形成修订证据 | 在给定样本和边界内经过外部试用 | 面试通过率、就业或薪酬提升 |

`A1` 不能被改写成“已验证有效”。v1.0 稳定版所要求的 H1/H2 证据只能来自真实试用，仓库不能用合成评分补齐。

## 5. 长任务的提交策略

长期实现使用一个功能分支，但保持版本级提交：

```text
v0.6 guided practice
-> v0.7 production case coverage
-> v0.8 reviewer calibration
-> v0.9 bilingual parity and archive
-> v1.0 release candidate
```

每个版本在进入下一版前执行本版新增校验和既有全量回归。最终发布前再从干净检出环境执行一次完整验证，生成与 commit 绑定的发布记录。

## 6. 不可跨越的边界

- 不采集或发布真实公司保密材料、泄露面试题和个人身份信息；
- 不把公开岗位描述推断成确定的内部面试流程；
- 不把合成案例、设计练习或作者自测写成生产经验；
- 不用模型生成的评分冒充独立评审者一致性；
- 不因为追求版本号而删除尚未完成的外部门禁；
- 不宣称面试通过率、录取率、薪酬提升或就业结果，除非未来存在可审计研究。

## 7. v1.0 的最终判断

自主实现可以完成 v1.0 发布候选所需的内容、结构和自动化证据。稳定版是否可以正式发布，还要检查 Roadmap 中依赖真实参与者的条目。如果这些条目未完成，版本必须标记为 release candidate，并明确列出缺口；这不是降级，而是项目可信度的一部分。
