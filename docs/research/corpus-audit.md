# 素材审计与项目设计决策

更新日期：2026-08-21

## 1. 审计范围

本项目启动前，对一套 FDE 面试资料进行了隔离解压、哈希去重、文本抽取和结构化审阅。源目录保持原样，没有把任何原始文件复制进公开项目。

审计后的规模如下：

| 项目                              |                         结果 |
| --------------------------------- | ---------------------------: |
| 原始目录大小                      |                    约 131 MB |
| 文件实例                          |                          333 |
| 按内容哈希去重后的独立文件        |                          196 |
| 独立 PDF                          |                          109 |
| 按规范化文本再次去重后的 PDF 内容 |                           86 |
| PDF 总页数                        |                        4,676 |
| PDF 估算总词数                    |                    约 114 万 |
| DOCX                              |                            7 |
| XLSX                              |                            3 |
| 压缩包                            | 10，均完成路径与链接安全检查 |

这组数字说明两个问题。第一，资料量确实很大，足以覆盖常见 FDE 面试主题；第二，文件数量会显著夸大知识量，因为同一手册、案例、题目或学习计划在多个版本中反复出现。因此，项目没有按“读完多少文件”组织，而是按候选人最终需要展示的能力重排。

## 2. 原始材料的强项

去重后，材料在以下方面覆盖较好：

- FDE 岗位的客户现场属性；
- 客户发现、问题拆解和需求澄清；
- RAG 的摄取、切分、检索、重排、引用和权限过滤；
- 常见系统设计、成本、延迟和上线问题；
- 故障排查、演示翻车恢复和利益相关者沟通；
- 模拟面试、评分表、行为面试和学习计划；
- Python/DSA 练习及部分参考解法；
- 一个小型企业助手代码样例，包含权限感知检索、PII 脱敏、提示词版本、评测和故障降级等概念。

这些内容构成了本指南的传统基本盘：FDE 不能只懂 AI，也不能只会讲客户；必须能把模糊现场转化为可测试、可上线、可交接的工程结果。

## 3. 需要修正的问题

### 3.1 重复不是深度

多份材料只是标题、版式或版本号不同，核心论述高度相似。继续把它们合并成更大的题库，只会增加检索成本。新项目用一条主线连接岗位、面试轮次、能力、案例和评分，不追求“500 道题”的视觉冲击。

### 3.2 题目多，校准少

很多问题带有参考答案，但较少解释面试官究竟观察什么、答案在哪些条件下成立、何时应该改变方案，以及“合格”和“优秀”之间的可观察差异。新项目把评分表和答案放在一起：答案是一个推理示范，评分表才是稳定的训练接口。

### 3.3 传统 RAG 较强，2026 Agent 工程不足

对 86 份独立 PDF 内容做关键词审计后，RAG、评测、生产故障和系统设计出现频繁；而 MCP、A2A 几乎没有覆盖，上下文工程、Agent Skills、可恢复长任务、Agent 身份与供应链安全也明显不足。

这与当期官方岗位要求存在错位。Anthropic 和 Vercel 的 FDE 描述已直接出现 MCP、sub-agent、skills、harness 等工程对象；Diligent 强调完整 Agent Development Life Cycle；MCP 2026-07-28 规范已经讨论无状态扩展、授权强化和 Tasks 扩展；A2A 1.0 把任务生命周期、断线后的异步更新和授权范围写入协议。新指南因此单独补齐这些内容。

### 3.4 样例代码能教学，但不能被误称为生产实现

附带代码样例的边界很清楚：它适合展示权限在检索前过滤、脱敏、提示词版本和安全失败等习惯，但向量检索和答案生成仍是本地占位实现。审计时在隔离 Python 3.12 环境安装锁定依赖后，14 项 pytest 全部通过，Ruff 静态检查通过；Bandit 未发现中高风险项，只对放在 `backend/evals/` 下的测试断言给出 5 个低风险 `assert_used` 提示。

进一步启动 API 做端到端请求时，`/health` 和 `/ask` 均正常返回，但“Acme Bank 续约风险”回答混入了 Helios Health 的无关证据，citation 列表还包含未用于正文的 Globex Retail；规则脱敏也把日期等内容误判为电话/姓名。这恰好暴露了“测试全绿不等于产品质量合格”：现有测试只确认有引用、目标名称出现和权限底线，没有约束检索精确度、引用—正文一致性和脱敏误报。这证明样例按自身测试契约可以运行，不等于完成了真实模型评测、性能/容量验证、第三方依赖威胁审计或生产安全认证。项目会把它当作“可运行但评测覆盖不足的教学样例”，不会包装成生产系统。

### 3.5 授权边界不明确

材料中出现“独立教育材料”“premium”等标识，但没有找到可以确认覆盖整套资料的开源再分发许可。公开 GitHub 项目因此遵循以下边界：

- 不上传原始 PDF、DOCX、XLSX、ZIP 或题库；
- 不复制大段原文或现成模型答案；
- 不把付费内容改个标题后重新发布；
- 仅发布原创的信息架构、解释、案例、问题和评分表；
- 涉及时效性事实时，优先引用公开的第一方来源。

## 4. 最终形成的能力模型

审计后，内容被压缩成八个可评分维度：

1. 客户发现与问题拆解；
2. 业务价值、产品判断与采用；
3. 编码、调试和端到端交付；
4. 数据工程与系统设计；
5. RAG、Agent 和模型应用工程；
6. 评测、可靠性、可观测性与成本；
7. 安全、权限、合规和上线治理；
8. 沟通、现场领导力、交接与产品化反馈。

这八个维度不是按文件目录推导出来的，而是把原始材料与当期官方岗位要求对齐后得到的。每个章节、案例和模拟面试都必须映射到至少一个维度。

## 5. 项目设计原则

### 原则一：先形成判断，再补知识

候选人不需要在所有主题上平均用力。先用评分表找到最危险的短板，再进入对应章节。

### 原则二：面试答案必须可追问

“使用 RAG”“加缓存”“做评测”都不算答案。强答案必须说明对象、指标、失败边界、上线顺序和回退路径，并能接受下一层追问。

### 原则三：生产责任贯穿全程

系统设计不是画完图就结束。答案要继续走到权限、数据变化、评测、灰度、成本、值班、事故复盘、采用率和客户交接。

### 原则四：项目经验最终要回到产品

一次项目成功不等于 FDE 组织成功。真正的杠杆来自把现场发现转成可复用的组件、标准、工具、文档和产品路线输入。

### 原则五：来源和时效可维护

岗位、协议和安全基线会变化。所有此类内容都通过结构化来源文件维护，保留历史快照，而不是把“2026 最新”永久写死在标题里。

## 6. 结论

原始资料提供了足够宽的基本盘，但公开项目的价值不在于重新打包，而在于完成三次转换：

1. 从文件堆转换为能力主线；
2. 从参考答案转换为可校准的推理训练；
3. 从 2024—2025 常见的 RAG/Agent 话题转换为 2026 的生产 Agent、协议、上下文、可靠性和治理问题。

这就是本 Fieldbook 的内容边界和建设依据。
