# 文档站点可行性评估

评估日期：2026-08-21

## 结论

v0.4 继续使用 GitHub 原生 Markdown，不新增文档站构建与托管链路。这个决定不是否定站点体验，而是当前读者问题主要来自入口、阅读顺序、语言和内容密度；加一个主题和搜索框不会自动解决这些问题，却会引入第二套餐单、URL、构建依赖和发布故障。

本轮优先完成英文学习地图、重点章节翻译、季度档案、清晰导航和无障碍写作约束。它们无论未来是否生成站点都可以复用。

## 评估标准

| 标准 | GitHub 原生 Markdown | 生成式文档站 |
| --- | --- | --- |
| 首次访问 | 仓库入口直接，熟悉 GitHub 的读者成本低 | 可以提供更清晰的侧栏与首页 |
| 搜索 | 依赖浏览器和 GitHub 搜索，跨章节体验一般 | 可提供全文搜索和过滤 |
| 双语导航 | 需要人工维护链接 | 可以按语言组织，但配置与翻译路由也要维护 |
| 可访问性 | 无 JavaScript 也能阅读，平台语义较稳定 | 取决于主题、组件和构建质量，需要持续测试 |
| 链接稳定性 | 文件路径即链接，历史清楚 | 需要 canonical、重定向和部署管理 |
| 贡献门槛 | 修改 Markdown 即可 | 贡献者可能需要本地 Node/站点工具链 |
| 维护成本 | 当前 CI 已覆盖链接、图表和内容结构 | 还需依赖升级、构建、预览、托管和故障处理 |

## 为什么此时不建

1. 当前内容仍在快速形成季度数据、案例和翻译结构，导航还没有经历两个发布周期；
2. 仓库的核心价值是内容、证据和练习，不应让前端工程成为主要维护负担；
3. 读者反馈尚未证明“找不到内容”主要由缺少站内搜索导致；
4. GitHub 原生阅读保留最低依赖和最透明的版本历史；
5. 同时维护 README、Markdown 导航和站点配置容易产生入口漂移。

## 何时重新评估

满足任意两项时启动小规模 spike：

- Markdown 文档超过 120 份，目录已经明显难以扫描；
- 至少五条独立读者反馈指向跨章节搜索或移动端导航，而不是内容本身；
- 中英文信息架构连续两个季度保持稳定；
- 有明确维护者愿意承担依赖升级、可访问性和部署故障；
- 社区需要版本化浏览历史快照，而 GitHub 入口已不足以表达。

## 未来 spike 的验收门槛

- Markdown 仍是唯一内容源，不复制第二份正文；
- 现有公开链接有重定向或稳定 canonical；
- 核心内容在禁用 JavaScript 时仍可阅读；
- 中英文导航不会把未翻译页面伪装成已完成；
- 搜索能按语言和内容类型过滤；
- 自动检查标题层级、内部链接、颜色对比和键盘导航；
- PR 有预览，主分支构建失败会阻止发布；
- 本地贡献流程不会比当前多出复杂服务依赖。

这个决策记录解决的是“现在要不要建站”，不是永久禁止。未来若证据变化，应更新本文和 `CHANGELOG.md`，而不是悄悄引入一套发布系统。
