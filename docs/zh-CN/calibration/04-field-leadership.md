# 答案校准四：现场领导力与产品化

> [!TIP]
> 现场判断题没有“客户第一”或“质量第一”的口号答案。你要保护的是决策质量、客户信任和可恢复交付，而不是自己的面子。

## Q11：客户要求明天演示，但系统还不稳定，怎么办？

### 面试官在观察什么

这道题同时考风险判断、沟通、技术降级和现场领导力。低分候选人往往在“通宵修好”和“拒绝演示”之间二选一；强候选人先确认演示要支持什么决定，再设计诚实、可控、可恢复的演示范围。

<details>
<summary><strong>2 分回答：靠加班和备用视频兜底</strong></summary>

> 我会优先修复问题、充分测试，准备备用环境和录屏。如果实在不行就跟客户解释延期。

这些动作都可能需要，但没有说明谁在看、演示要证明什么、哪些不稳定会误导决策，也没有明确到什么条件必须停止现场操作。

</details>

<details>
<summary><strong>3 分回答：缩小演示契约并准备降级</strong></summary>

> 我先确认明天的观众和决策目标。如果只是验证一个工作流是否值得继续，我会把演示收缩到已经通过测试的 golden path，冻结数据、模型和配置，关闭未验证功能。准备明确的人工步骤、只读降级和录屏，但不会把录屏冒充实时结果。演示前做一次故障彩排，定义继续、切换和停止条件，并提前告诉客户哪些部分是已验证能力、哪些仍是假设。

这段回答保护了演示的真实性，也给出了可执行降级路径。

</details>

<details>
<summary><strong>4 分回答：把演示变成一次受控决策，而不是舞台表演</strong></summary>

> 我先问清楚演示后谁要做什么决定。面向高管的价值确认、面向安全团队的控制评审和面向一线用户的可用性测试，不应该使用同一脚本。然后按决策目标定义最小证据，冻结可变项，给每一步设置观测和切换点。能安全暴露的限制我会主动讲，因为客户迟早会在生产里遇到；可能造成越权、错误动作或错误承诺的问题不能用“演示环境”掩盖。若当天发现阻断风险，我会带着替代方案沟通：展示已验证链路、用录屏说明未稳定部分、给出复现证据和下一次验收日期。信任比一次顺滑表演更难恢复。

4 分回答把演示与决策人、风险等级和长期信任连接起来，也能在拒绝某些展示时给出替代证据。

</details>

### 演示前一页检查卡

| 项目       | 必须写清                                     |
| ---------- | -------------------------------------------- |
| 观众与决定 | 谁看；演示后要批准、否决还是提出什么反馈     |
| 已验证范围 | 哪条路径、哪份数据、哪个版本、哪些权限       |
| 已知限制   | 哪些场景尚未验证，是否会影响当前决定         |
| 失败注入   | 网络慢、工具失败、模型拒答时怎样表现         |
| 降级路径   | 实时演示、只读结果、录屏、白板解释的切换条件 |
| 现场角色   | 谁讲、谁操作、谁观察日志、谁决定停止         |
| 后续证据   | 演示结束后交付什么，不把掌声当验收           |

### 落到企业现场

演示前最后一次排练不要只跑成功路径。拔掉一个依赖、让一个工具超时、输入一个无答案问题，观察团队是否知道谁说话、谁切换、谁记录。真正伤害客户信任的通常不是出现错误，而是团队面对错误时开始互相找人和现场编解释。

## Q12：如何把一次客户定制变成产品能力？

### 面试官在观察什么

“做成可配置模块”只是技术复用。真正的产品化还要判断问题是否跨客户重复、变化维度是否稳定、谁维护、默认策略是什么，以及抽象成本是否值得。

<details>
<summary><strong>2 分回答：抽象公共代码</strong></summary>

> 我会把客户定制中的通用部分抽成组件，通过配置支持不同客户，再补充文档和测试供其他项目复用。

这是良好的工程习惯，但没有证明其他客户有同样问题，也没有处理产品 owner、升级兼容和现场例外如何退出。

</details>

<details>
<summary><strong>3 分回答：先识别重复问题，再稳定变化接口</strong></summary>

> 我会区分一次性环境差异和重复出现的产品缺口。只有在多个现场看到相同工作流、相似风险和可稳定表达的变化维度时，才进入产品化。先记录哪些规则必须统一、哪些允许配置、哪些仍需要扩展点，再补契约测试、迁移方式、观测和 owner。第一个客户的实现可以作为验证，但不能直接成为所有客户的默认模型。

这段回答从“复用代码”前进到“验证问题和变化维度是否稳定”。

</details>

<details>
<summary><strong>4 分回答：建立现场反馈进入产品路线的证据机制</strong></summary>

> 我会为现场发现建立一份 field-to-product memo：问题出现在哪些客户、当前绕行成本、如果不解决影响什么、共性与差异分别是什么、现有平台为什么覆盖不了。然后和产品、平台、安全和实施团队一起判断四种去向：产品核心能力、受支持扩展点、行业模板，或者明确保持客户定制。进入产品路线后要定义迁移和退出计划，让客户逐步离开临时分支；同时用采用、支持成本和新项目交付时间验证抽象是否真的产生杠杆。如果只把复杂性搬进一个巨大配置文件，不能算产品化成功。

4 分回答说明了谁参与决策、有哪些可能去向、客户定制如何退出，以及怎样证明复用产生了组织收益。

</details>

### 一页 field-to-product memo

```text
现场问题：哪段工作流被什么约束阻塞
证据范围：出现在哪些客户/行业；哪些仍是单点现象
当前代价：人工绕行、事故、交付周期、支持负担
共同核心：不随客户改变的语义和控制
变化维度：可配置、可扩展、必须隔离的部分
候选去向：产品能力 / 扩展点 / 行业模板 / 保持定制
产品代价：兼容、迁移、安全、文档、运维 owner
验证指标：采用率、交付时间、缺陷率、支持成本
反证条件：出现什么证据说明不应继续抽象
```

### 落到企业现场

不要等项目结束才“总结可复用经验”。每周维护现场模式日志：问题、证据、临时解、第二个出现位置和潜在 owner。产品化会议只讨论有多个证据点的条目；单一客户的强烈声音可以提高调查优先级，但不能自动代表市场共性。

## 完成这一组后的自检

你应该能够做到：

- 在拒绝高风险演示时同时提供可前进的替代方案；
- 区分“现场表现稳定”和“产品已经可以上线”；
- 区分代码复用、交付模板、扩展点和产品核心能力；
- 用证据说明为什么一个客户需求值得或不值得产品化；
- 讲清临时定制如何退出，而不是永久留在系统里。
