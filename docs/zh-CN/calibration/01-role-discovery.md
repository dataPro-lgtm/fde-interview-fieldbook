# 答案校准一：岗位、发现与范围

> [!TIP]
> 先用手机录下自己的回答，再展开示例。这里要校准的是判断顺序，不是普通话、语速或话术。

## Q1：你如何解释 FDE？它与解决方案架构师或普通软件工程师有什么不同？

### 面试官在观察什么

这不是一道岗位百科题。面试官要确认你是否理解 FDE 对“客户结果、亲手工程和产品反馈”三者同时负责，也会观察你有没有把相邻岗位说成低一等的角色。

<details>
<summary><strong>2 分回答：定义正确，但像职位说明书</strong></summary>

> FDE 是连接客户和研发的桥梁，既需要和客户沟通需求，也需要写代码解决问题。和普通软件工程师相比，FDE 更贴近客户；和解决方案架构师相比，FDE 写代码更多。

这段话没有明显错误，但“桥梁”“更贴近”“写得更多”都无法说明责任边界。面试官还不知道你怎样判断任务成功，也不知道现场学习如何回到产品。

</details>

<details>
<summary><strong>3 分回答：说明端到端责任和岗位差异</strong></summary>

> 我把 FDE 理解为对客户工作流结果负责的工程师。工作通常从发现和技术界定开始，接着亲手做出最小端到端闭环，推进到真实环境，再通过采用、质量和故障数据判断它是否产生价值。普通软件工程师往往对产品或平台边界负责，解决方案架构师更常负责方案与技术路径；FDE 的特殊之处，是在客户现场同时承担问题定义、实现和上线学习。具体边界会因公司而变，所以我会先看职位是否明确要求 production code、deployment ownership 和 product feedback。

这段回答可以独立支撑后续追问：它给出了工作起点、结束条件和岗位差异，也主动承认不同公司的 FDE 不完全相同。

</details>

<details>
<summary><strong>4 分回答：把岗位理解落到组织杠杆</strong></summary>

> 我不会把 FDE 简化成“更会写代码的售前”或“更会见客户的软件工程师”。它存在的原因，是产品能力和客户现实之间总有一段无法靠文档、接口和标准实施完全消除的距离。FDE 要进入这段距离：先确认真正阻塞业务的是工作流、数据、权限、模型还是组织问题，再用最小闭环证明价值和风险。如果只是为一个客户交付完就离开，组织杠杆仍然很低；成熟 FDE 还要把共性问题沉淀成产品能力、实施标准或平台反馈。我的匹配点是……

4 分的关键不是措辞更高级，而是解释了岗位为什么存在、一次交付如何形成组织杠杆，并自然转入个人证据。最后一句必须由你的真实经历完成。

</details>

### 评分证据

| 观察点   | 2 分             | 3 分                   | 4 分                             |
| -------- | ---------------- | ---------------------- | -------------------------------- |
| 成功定义 | 沟通并完成项目   | 工作流结果、上线与采用 | 结果之外还能沉淀复用能力         |
| 工程责任 | 只说“会写代码”   | 发现、实现、发布闭环   | 能处理产品与现场之间的结构性缺口 |
| 岗位边界 | 用工作量区分岗位 | 用责任对象区分岗位     | 承认不同公司的边界并说明判断证据 |

### 两层追问

1. **“如果客户只需要配置，不需要写代码，还算 FDE 项目吗？”** 先看是否仍存在需要现场判断和结果责任的复杂性；代码量不是岗位定义。
2. **“讲一次你把现场问题反馈成产品能力的经历。”** 没有真实经历时要明确说尚未做过，再讲你会如何识别共性、验证复用范围和进入产品路线。

### 落到企业现场

真正进入项目后，先写一页 `engagement contract`：业务结果由谁负责、FDE 对哪些技术决策负责、客户团队必须提供什么、哪些事项仍由产品或平台团队拥有。很多现场问题不是技术难，而是三周后大家才发现对“交付完成”的理解不同。

## Q2：客户说“我们需要一个 Agent”，你第一步做什么？

### 面试官在观察什么

核心不是你会不会设计 Agent，而是你能否把客户提出的解法退回到待验证的问题，并在不冒犯客户的前提下重建共同任务。

<details>
<summary><strong>2 分回答：会澄清，但默认答案仍是 Agent</strong></summary>

> 我会先问客户 Agent 要完成哪些任务、调用哪些工具、使用什么模型，然后设计规划、记忆和工具调用模块，并增加人工审核。

问题在于，所有澄清都发生在 Agent 方案内部。候选人没有验证客户真正需要的是自治执行、确定性工作流、搜索建议，还是现有流程修复。

</details>

<details>
<summary><strong>3 分回答：先还原工作流，再选择自动化形态</strong></summary>

> 我不会先讨论模型和框架。我会请客户带我走一遍当前流程：谁触发、输入是什么、人在什么地方判断、要调用哪些系统、失败代价多大，以及今天最耗时或最容易错的步骤。然后把需求拆成检索、判断、生成和动作，比较规则、普通工作流、Copilot 和 Agent。只有当任务路径确实动态、需要根据中间结果选择下一步，而且动作风险可以约束时，我才会选择 Agent。

这段回答把“Agent”降级为候选方案，也给出了选择依据。

</details>

<details>
<summary><strong>4 分回答：用最小实验同时验证价值与自治风险</strong></summary>

> 我会先接受客户想解决的问题，但暂不接受 Agent 是唯一解法。第一轮发现要拿到三类事实：当前工作流和基线、哪些判断必须动态完成、哪些错误不可接受。然后选择一个真实但可逆的薄切片，例如只生成建议、不直接执行动作，用历史任务回放比较规则流程、Copilot 和受限 Agent。准入指标不只看任务完成率，还要看越权动作、人工接管、恢复成本和用户是否真的采用。如果确定性流程已经解决主要问题，我会明确建议不要上 Agent。

4 分来自两点：用对照实验而不是偏好选架构；把“停止使用 Agent”也定义成一种成功结论。

</details>

### 评分证据

| 观察点   | 2 分            | 3 分                             | 4 分                         |
| -------- | --------------- | -------------------------------- | ---------------------------- |
| 问题重构 | 在 Agent 内澄清 | 回到当前工作流                   | 明确把 Agent 当作待验证假设  |
| 方案选择 | 默认 Agent      | 比较规则、工作流、Copilot、Agent | 用对照实验和停止条件做选择   |
| 风险     | 笼统说人工审核  | 看动作风险和权限                 | 同时测越权、接管、恢复与采用 |

### 两层追问

1. **“客户已经向老板承诺 Agent 了，怎么办？”** 不争论名词，提出一个仍可称为 Agent 试点、但动作受限且能快速产生证据的方案。
2. **“什么情况下你会直接拒绝？”** 当需求要求不可逆高风险动作，却没有可验证权限、审批、幂等、审计或人工接管条件时，应暂停自动执行。

### 落到企业现场

第一次工作坊不要画 Agent 架构，先把一张真实工单从触发走到结束。记录每一步的输入、判断人、使用系统、等待时间、返工和失败后果。会后交付的不是会议纪要，而是 `current-state workflow + assumptions + open evidence`。这张图决定后续该做搜索、Copilot、工作流还是 Agent。

## Q3：怎样把模糊需求变成两周可交付的 thin slice？

### 面试官在观察什么

Thin slice 不是缩水版大系统，而是用最小投入获得最大决策信息的真实闭环。它必须触达真实输入、真实用户和真实结果，同时主动砍掉不影响当前判断的范围。

<details>
<summary><strong>2 分回答：把功能列表缩短</strong></summary>

> 我会先做 MVP，只保留最核心的几个功能，两周内完成，然后根据客户反馈继续迭代。

“核心功能”没有选择依据，也没有说明如何证明价值。很多失败项目正是从一个功能较少、但仍然没有真实用户和真实数据的 Demo 开始。

</details>

<details>
<summary><strong>3 分回答：选择一个真实端到端路径</strong></summary>

> 我会先定义两周后必须回答的决策，例如“系统能否把一线客服查找政策的时间降低，同时不发生跨租户引用”。然后只选择一个团队、一个知识域和一种高频问题，接真实身份、真实文档和真实反馈。先以建议模式运行，保留人工确认。非目标会明确写出，例如暂不处理多语言、自动执行和全部历史系统。验收同时看任务时间、引用支持率、权限错误和实际使用。

这是一个可以真实失败、也能产生下一步决策证据的薄切片。

</details>

<details>
<summary><strong>4 分回答：优先验证最危险的未知，而不是最好演示的路径</strong></summary>

> 我会先列出价值、可行性、采用和风险四类最大未知，再选择一次端到端试验尽可能同时击中它们。假设最大风险不是模型质量，而是权限和文档更新，我不会先做一个漂亮聊天界面，而会选真实身份、真实删除传播和一个可测工作流。两周计划包含进入条件、每天能看到的中间证据、失败隔离、非目标和停止条件。到期后必须做决定：扩大、修改假设，还是停止，而不是默认进入下一阶段。

4 分回答把 thin slice 变成了决策工具，并且接受“试验结束后停止项目”这一可能结果。

</details>

### 评分证据

| 观察点 | 2 分          | 3 分                 | 4 分                           |
| ------ | ------------- | -------------------- | ------------------------------ |
| 范围   | 少做几个功能  | 一个真实端到端路径   | 选择信息价值最高的路径         |
| 验收   | 收集反馈      | 业务、系统和风险指标 | 进入、停止和下一步决策条件齐全 |
| 现实性 | 容易变成 Demo | 真实身份、数据、用户 | 主动验证最危险未知和失败恢复   |

### 两层追问

1. **“两周接不完真实系统怎么办？”** 可以使用受控快照或人工桥接，但必须保留真实权限和数据语义，并明确它没有验证哪些集成风险。
2. **“客户不同意缩范围怎么办？”** 不说“资源不够”，而是展示每项范围对应的决策价值、依赖和风险，请决策人明确优先级及延期代价。

### 落到企业现场

Thin slice 必须写成一页契约：目标用户、触发、真实输入、系统动作、人工动作、成功指标、阻断指标、非目标、依赖、负责人和到期决策。缺少“非目标”和“到期决策”的 MVP，往往会悄悄变成长周期项目。
