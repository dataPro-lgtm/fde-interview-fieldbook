# 编码、数据与交付基本功

## 1. 为什么 FDE 仍然要过硬编码

客户现场最昂贵的问题常常没有整洁复现环境：一个脏字段触发批量失败、一个权限过滤顺序造成泄漏、一个重试让外部动作执行两次、一个看似无害的 schema 变化让整条管道沉默。FDE 需要在信息不全和时间压力下读代码、写代码、验证假设并安全恢复。

编码轮并不只是筛算法。它在观察你的工程工作方式是否可预测：

- 会不会先确认输入、输出和边界；
- 能否把问题拆成可测试部分；
- 能否写出别人可以接手的代码；
- 出错后是随机修改，还是利用证据定位；
- 是否意识到数据、并发、重试和副作用。

## 2. 三类常见编码形式

### 算法与数据结构

考察基础抽象、复杂度和实现熟练度。FDE 不应以“工作中用不到”为理由轻视它；客户现场需要快速处理集合、窗口、图、调度和缓存问题。

高收益主题：哈希表、双指针、滑动窗口、栈/队列、区间、堆、树/图遍历、拓扑排序、二分、简单动态规划。

### 实际应用构建

可能要求实现 API、解析数据、聚合日志、调用外部服务、加缓存或扩展已有项目。观察接口设计、错误处理、测试和迭代速度。

### 调试与代码阅读

给出失败测试、日志或代码库，要求定位问题。这里尤其看重假设排序、最小复现、观测点和风险控制。

具体形式必须向招聘方确认，不要用一种训练覆盖所有岗位。

## 3. 现场编码的稳定流程

### 读题并复述契约

说明输入、输出、错误语义、数据规模和是否允许修改输入。不要用五分钟重复题目，但要消除会改变算法的歧义。

### 手算两个例子

一个正常例子，一个边界或反例。例子不仅验证理解，也帮助你发现状态和不变量。

### 先给可工作的方案

说出最直接方案和复杂度，再讨论是否需要优化。直接跳到最优解却解释不清，信号通常不如先建立正确性。

### 明确不变量

例如滑动窗口中“窗口内始终满足什么条件”，或重试逻辑中“每个业务键最多产生一次外部副作用”。不变量比逐行描述代码更能显示思考。

### 小步实现并自测

优先完成主路径，再补边界。每写一段，用刚才的例子走一遍。卡住时说出已知事实和下一步验证，不要沉默地大改。

### 收尾

给出时间/空间复杂度、剩余风险、生产化还需补什么。不要无限扩展到完整系统。

## 4. FDE 风格的数据题

### Schema 演进

客户 API 新增、删除或改变字段类型时，强答案会讨论版本兼容、默认值、隔离坏记录、契约测试、监控和回放，而不只是 `try/except`。

### 幂等与重复

“消息至少投递一次”意味着消费者可能重复执行。需要业务幂等键、去重状态、外部动作的请求键和重放策略。仅在内存 `set` 去重无法跨进程、跨重启或长期扩展。

### 迟到和乱序

事件时间与处理时间不同。要说明窗口、watermark、补算、最终一致性和报表修正，而不是假设输入有序。

### 删除与更新

知识库或索引同步不能只做 append。需要稳定文档标识、版本、内容哈希、upsert、软删除、墓碑传播、权限变化、重建和一致性校验。

### 租户与权限

过滤应该尽可能在数据访问和检索之前发生；不能把所有数据送进模型后再要求“不要泄漏”。测试要包含跨租户 canary 和越权查询。

## 5. API 与外部工具设计

一个生产可用的工具接口应让调用者容易做对、难以做错。

需要明确：

- 输入 schema、枚举、必填项和大小限制；
- 身份和授权在何处校验；
- 超时、重试、速率限制和熔断；
- 请求是否只读、可逆或有副作用；
- 幂等键和重复调用语义；
- 错误是可重试、需要用户修正还是永久失败；
- 日志里哪些字段必须脱敏；
- 版本兼容和弃用策略。

对于 Agent 工具，描述要清晰且职责尽量不重叠。多个含义相近的工具会增加模型选错概率。高风险动作应拆成“准备/预览”和“确认执行”两步。

## 6. 测试不只是行覆盖率

### 单元测试

验证纯逻辑、边界和错误分支。适合快速定位。

### 契约测试

验证上下游 schema、状态码、字段语义和兼容性。客户集成中极其重要。

### 集成测试

验证数据库、队列、对象存储、模型或工具组合后的真实行为。

### 回放与回归

把历史真实输入重新执行，检查变更是否破坏关键场景。AI 系统的黄金集也是一种回归资产。

### 故障注入

主动模拟超时、限流、半失败、重复消息、陈旧数据和权限拒绝，验证系统是否安全退化。

### 安全测试

越权、跨租户、提示注入、恶意文件、工具参数注入、敏感日志和供应链问题必须作为独立测试类别。

## 7. 一次生产调试的 TRACE 路径

本项目使用 TRACE 作为事故回答骨架：

```text
T — Triage impact       影响谁、多少、多久、是否仍在扩大。
R — Reproduce & segment 用最小样本复现，按版本/用户/数据/地区分桶。
A — Attribute by layer  沿数据、检索、模型、工具、状态、依赖逐层归因。
C — Contain & recover   限流、降级、回滚、隔离、人工接管并恢复服务。
E — Evaluate & prevent  补监控、测试、门禁、runbook 和所有权。
```

TRACE 的顺序很重要。事故中第一目标通常是控制影响，不是证明根因。回滚后仍要保留样本和 trace，否则恢复了服务却失去了学习机会。

## 8. 数据同步题应该怎样回答

题目：知识库每天变化，如何做生产级同步？

一个完整回答至少覆盖：

1. **身份**：`doc_id` 稳定代表逻辑文档，版本或内容哈希代表具体内容；
2. **捕获变化**：CDC、事件、增量 API 或定期快照，根据源系统能力选择；
3. **去重与顺序**：事件 ID、版本号、幂等 upsert，拒绝旧版本覆盖新版本；
4. **软删除**：源系统删除或失权先写 tombstone，使检索立即不可见，再异步物理清理；
5. **派生状态**：解析、切分、embedding、索引各自有版本和状态，不能只标“同步成功”；
6. **权限变化**：权限是内容的一部分，变更必须触发可见性更新；
7. **回放与重建**：保留可重建的原始/规范化层和 checkpoint；
8. **一致性验证**：源计数、目标计数、hash 抽样、陈旧率、孤儿 chunk、删除传播延迟；
9. **隔离坏数据**：DLQ 或 quarantine，不让单文档阻塞全批次；
10. **观测与 SLO**：端到端新鲜度、成功率、积压、重试、删除延迟。

这类回答能同时展示数据工程、RAG 和生产责任，比单纯说“用 Kafka + Spark”强得多。

## 9. 速度与质量如何取舍

FDE 经常被要求“两周交付”。成熟做法不是降低所有质量，而是区分可逆与不可逆决策：

- UI 样式、部分算法和内部实现通常可快速迭代；
- 数据泄漏、不可逆动作、审计缺失、错误迁移和无法回滚的 schema 需要更早保护；
- 先使用人工复核可以降低自治风险，但必须测量人工负担；
- 临时实现要有退出条件、负责人和清理日期，否则会永久化。

一句高质量表达是：

> 我会缩小功能范围和自动化程度，但不缩掉租户隔离、审计、回滚和关键验收，因为这些一旦出错会伤害客户信任，而且后补成本更高。

## 10. 如何准备

每周至少安排三种练习：

1. 两次 40 分钟限时编码，必须口述并写测试；
2. 一次真实数据处理小题，包含坏记录、重复、更新和删除；
3. 一次 30 分钟代码阅读或事故调试，用 TRACE 复盘。

记录的不是“做了多少题”，而是错误类型：读题、边界、语言熟练度、复杂度、测试、调试、沟通或生产语义。连续两周集中修最高频错误。
