# 2026 生产 AI 必修课

> [!NOTE]
> **适合谁：** 会做 Demo，但对评测、权限、恢复、成本和变更治理缺少完整结构的人<br>

## 1. 生产 AI 的本质不是模型调用

模型调用只是一次概率计算。产品需要的是一个可预测的工作系统：拿到正确上下文，在正确权限下选择允许的动作，经历故障后仍能恢复，并用持续证据证明质量和价值。

可以把生产 AI 拆成六个平面：

1. **数据平面**：事实、文档、事件、版本、权限和新鲜度；
2. **上下文平面**：指令、工具、示例、检索结果、历史和记忆；
3. **执行平面**：模型、工作流、Agent、工具、状态和审批；
4. **控制平面**：配置、提示、策略、版本、发布、回滚和预算；
5. **证据平面**：trace、日志、评测、反馈、审计和业务指标；
6. **治理平面**：身份、最小权限、数据用途、安全、合规和责任。

面试中如果只讨论模型和向量库，剩下五个平面会成为追问缺口。

## 2. RAG：先分层诊断，再谈优化

### 2.1 一条完整链路

```text
源数据 -> 变化捕获 -> 解析 -> 规范化 -> 切分 -> embedding/index
     -> 权限过滤 -> 候选召回 -> 重排 -> 上下文组装
     -> 生成 -> 引用校验 -> 产品呈现 -> 用户反馈
```

每层都可能让最终答案失败。更强模型无法读取没进库的文档，也无法修复被错误权限过滤掉的政策。

### 2.2 五类常见失败

1. **语料失败**：源缺失、OCR 错、版本旧、删除未传播；
2. **权限失败**：该看的看不到，不该看的被召回；
3. **检索失败**：正确块未召回或排序靠后；
4. **上下文失败**：切分破坏语义、冲突版本混入、上下文过长；
5. **生成/产品失败**：模型误读、引用不支持、表达不适合用户、用户不信任。

调试时给每个失败样本标注“第一个出错层”，否则团队会用总体分数争论。

### 2.3 评测分解

- 语料：覆盖率、解析成功率、权限完整率、新鲜度、删除延迟；
- 检索：recall@k、MRR/nDCG、正确版本命中、越权命中为零；
- 生成：事实支持、引用正确、完整性、拒答正确、格式；
- 端到端：任务成功、处理时间、采纳/改写、升级和风险错误；
- 运营：p95 延迟、成本、失败率、积压和恢复时间。

LLM-as-a-judge 可以扩展评测，但需要人工校准、明确 rubric、顺序/长度偏差检查和 judge 版本记录。高风险事实最好有确定性验证或专家复核。

## 3. 知识库更新：upsert 与软删除的边界

### `doc_id` 表示逻辑身份

文档标题和 URL 都可能变化。`doc_id` 应稳定代表业务对象；内容哈希和 `version` 代表具体版本。若业务对象发生实质分裂或合并，应产生新身份并记录关系，而不是强行覆盖。

### Upsert 适用于仍存在的逻辑对象

内容、元数据或权限变化时，写入新版本，派生 chunk/embedding/index 也带版本。只有新版本完全可用后再切换读取，避免半更新。

### 软删除适用于“立即不可见、稍后清理”

源删除、访问权撤回、保留期结束或文档被判无效时，先写 tombstone，让查询路径立即排除；后台再删除向量、chunk、缓存和对象副本。软删除不是永久保存，而是提供审计、传播和恢复窗口。

### 必须定义四个时钟

1. 内容更新多久可见；
2. 权限撤销多久生效；
3. 删除多久从所有读路径消失；
4. 物理数据多久彻底清理。

“每天同步一次”不能回答这些安全与产品问题。

## 4. Agent：先证明需要自治

### 4.1 工作流和 Agent 的边界

确定性工作流由代码选择步骤；Agent 由模型基于上下文选择步骤。两者可以组合：关键流程用状态机约束，局部不确定任务交给模型。

适合 Agent 的条件：路径取决于中间观察、工具多且组合难穷举、结果可验证、失败可停止/补偿、自治价值足够高。

不适合的条件：固定步骤、规则清楚、错误不可承受、无法验证结果、权限边界模糊或简单表单/按钮已足够。

### 4.2 Agent 最小生产契约

必须明确：

- 目标和完成条件；
- 可使用的工具和数据；
- 最大步骤、时间和费用；
- 状态持久化和恢复；
- 工具超时、重试、幂等和副作用；
- 需要人工确认的动作；
- 停止、拒绝、降级和升级条件；
- trace 与评测记录；
- 身份、权限和审计。

没有这些，所谓 Agent 只是一个可能无限循环的模型调用器。

### 4.3 多 Agent 不是默认升级

拆 sub-agent 的理由应该是上下文、权限、工具、并行性或评测边界不同，而不是“任务看起来复杂”。

合理拆分示例：研究 Agent 只读外部资料，执行 Agent 只能调用受限内部工具，审核 Agent 使用独立证据做检查。每个 Agent 的权限和成功标准清楚。

不合理拆分：planner、researcher、writer、critic 共享同样上下文和工具，只增加转发、延迟、成本和错误归因难度。

默认由主 Agent 与用户保持统一对话。只有子任务需要独立授权、长时间异步协作或专业人机交互时，才让 sub-agent 直接与用户交流，并明确身份和状态。

## 5. 上下文工程：管理稀缺且敏感的运行时资源

上下文不仅是 prompt。它包括系统指令、工具定义、few-shot、检索文档、消息历史、记忆、用户身份和运行状态。

### 常见失败

- 工具太多且职责重叠，模型难以选择；
- 长历史把旧目标和错误假设带入当前任务；
- 检索内容含恶意指令，被误当系统要求；
- 记忆没有来源、过期或被污染；
- 上下文包含不必要 PII，并被 trace 永久记录；
- 为覆盖所有边缘情况，把提示写成脆弱规则引擎。

### 管理策略

- 最小充分指令，结构清楚但不过度硬编码；
- 工具少而清晰，返回 token-efficient 结果；
- 用多样、代表性的 canonical examples，而不是堆边缘规则；
- just-in-time 获取上下文，按任务动态加载；
- 历史压缩时保留目标、决定、未完成事项和证据来源；
- 记忆带来源、作用域、版本、时间和撤销机制；
- 不可信文档永远视为数据，不提升为指令。

## 6. Agent Skills：把程序性知识按需装载

Skill 的价值不是增加一个 prompt 文件，而是把可复用工作方法组织为按需加载的说明、参考资料和确定性脚本。渐进披露可以避免所有知识一开始塞进上下文。

适合用 Skill：

- 流程跨多个任务复用；
- 需要组织特定步骤、模板或验证；
- 部分操作适合确定性脚本；
- 能定义触发条件和验收用例。

不适合用 Skill：

- 必须由强约束状态机执行的高风险流程；
- 只是一次性提示；
- 需要稳定低延迟 API 的基础能力；
- 把权限控制写进说明而没有系统强制。

Skill 应从评测失败出发增量建设，而不是先写一本庞大手册期待 Agent 自己理解。

## 7. MCP：工具互联之后，治理更重要

MCP 解决的是模型/Agent 与工具、资源、提示等能力之间的标准化连接。2026-07-28 规范强调无状态可扩展核心、路由与计量头、列表缓存、授权强化，以及独立 Tasks 扩展。

面试中不要只会说“用 MCP 接工具”。继续回答：

- server 如何被发现和信任；
- client 用谁的身份授权；
- token 的 audience、scope 和生命周期；
- 工具 schema 如何版本化；
- 输出是否含不可信内容；
- 高风险动作怎样审批和幂等；
- server 供应链、更新和撤销如何管理；
- 长任务状态属于 MCP Tasks、业务工作流还是专用编排器；
- 连接器故障如何隔离和降级。

MCP 降低了接入成本，也扩大了攻击面。接得快不等于可上线。

## 8. A2A：Agent 之间传递的是任务，不是随意聊天

A2A 1.0 定义 Agent 的发现、消息、任务、流式状态、订阅、推送和授权范围。它适合独立、可能由不同团队或系统拥有的 Agent 协作。

关键设计问题：

- 对方 Agent 的能力和身份如何验证；
- 任务 ID、上下文和产物如何持久化；
- 哪些状态是终态，取消和重复请求如何处理；
- 断线后用订阅、轮询还是 webhook 恢复；
- 输入和产物如何验证，不能把对方输出直接当可信指令；
- 跨 Agent 权限是否被放大；
- 故障责任和 trace 如何贯通。

如果同一进程内的两个模块函数调用就能解决，不需要为了“多 Agent”引入跨系统协议。

## 9. 可恢复长任务：把执行与连接解耦

网页关闭后任务仍继续，靠的不是把请求重新打回原 Pod，而是把任务状态放在独立、持久的执行层。

典型结构：

```text
POST /tasks -> 返回 task_id
                 |
                 v
durable workflow / queue + workers
  - 持久状态
  - checkpoint
  - retries / backoff
  - idempotency
  - approval signals
  - cancellation
                 |
                 v
event store / artifacts
                 |
GET /tasks/{id} 或 SSE/WebSocket 重新订阅
```

浏览器连接只是观察通道，不是任务生命线。多 Pod 下无需粘性会话；任何 API Pod 都能根据 `task_id` 读取状态或订阅事件。Redis 可以做短期 pub/sub 或缓存，但任务事实、幂等与审计通常需要更耐久的数据库/工作流引擎。

成熟实现还要处理：worker 崩溃后的重放、写工具的重复副作用、事件序号、断点续传、输出分片、保留期、取消竞态和部署版本兼容。

## 10. 评测：把“感觉不错”变成变更控制

### 黄金集如何形成

来源应包括高频正常样本、边界长尾、对抗样本、多跳任务、历史事故、不同角色和真实复杂工单。每个样本记录来源、标签、风险等级、预期行为和可接受变体。

### 反例怎样设计

好的反例不是随便问一个错误问题，而是针对一条系统边界：

- 无答案问题测试正确拒答；
- 相似但过期政策测试版本选择；
- 跨租户诱导测试权限；
- 文档内恶意指令测试间接提示注入；
- 工具参数包含危险值测试校验；
- 长对话目标漂移测试上下文；
- 重试同一写操作测试幂等；
- 多个局部正确结果组合成错误动作测试级联失败。

反例必须有明确期望、失败严重度和归因层，否则只能产生“模型答错了”的噪声。

### 发布门禁

按风险设置门禁：总体质量可以允许小幅波动，权限泄漏、不可逆工具误用和高风险错误应为阻断项。任何模型、提示、工具、检索、知识库或策略变更都需要可归因版本。

## 11. 可观测性：记录足够证据，但不要制造新泄漏

建议至少关联：

- request/task/trace ID；
- 用户与租户的非敏感标识；
- 模型、提示、工具、策略和知识库版本；
- 检索文档 ID 与分数；
- Agent 步骤、工具选择、状态和终止原因；
- 延迟分解、token、缓存和成本；
- 评测标签、人工反馈和业务结果。

OpenTelemetry 已定义 GenAI 相关语义属性，但也明确提醒输入消息、检索查询、工具参数和结果可能包含敏感信息。生产默认不应完整记录所有 prompt 和文档正文；使用采样、哈希、结构化摘要、字段白名单和严格访问控制。

## 12. Agent 安全：安全与可靠性在部署层汇合

OWASP Agentic Top 10 涵盖目标劫持、工具误用、身份/权限滥用、供应链、意外代码执行、记忆污染、不安全 Agent 通信、级联失败和人类信任利用等风险。

面试中可以用四个控制层回答：

### 身份与最小权限

短期、限定 audience/scope 的凭证；尽量使用用户委托；按工具和数据域分权；高风险动作 step-up auth。

### 数据与指令隔离

把外部内容视为不可信数据；权限前置；敏感上下文最小化；记忆有作用域和撤销。

### 动作治理

schema 校验、允许列表、幂等、预算、最大步骤、审批、沙箱、补偿和 kill switch。

### 证据与响应

不可抵赖审计、异常检测、红队评测、供应链清单、事故 runbook 和凭证撤销。

“加 guardrail”不是答案；必须说 guardrail 在哪一层、强制什么不变量、失败时怎样处理。

## 13. 成本与延迟：先做预算，再做技巧

把端到端延迟拆成排队、检索、模型首 token、生成、工具和后处理；把成本拆成输入、输出、缓存、检索、工具、重试和人工复核。

优化顺序通常是：

1. 移除不必要调用和上下文；
2. 并行独立步骤；
3. 缓存稳定前缀、检索或工具结果；
4. 路由简单任务到小模型；
5. 限制步骤和输出；
6. 批处理非交互任务；
7. 最后再做更复杂基础设施优化。

Prompt cache 便宜，是因为提供商可复用相同前缀的中间计算，减少重复 prefill；它通常存在提供商管理的短期缓存中，不等于把答案存进普通 Redis。是否支持取决于模型架构、基础设施、隐私隔离、命中率和计费产品设计。面试时要说明缓存键、前缀稳定性、租户隔离、TTL、失效和命中监控。

## 14. 一条贯穿面试的生产检查表

面对任何 AI 设计，最终都问：

1. 正确任务是什么，为什么值得自动化？
2. 哪些事实和权限进入上下文？
3. 为什么是 RAG、工作流或 Agent？
4. 状态在哪里，断线和重启后怎样恢复？
5. 工具如何授权、验证、幂等和审批？
6. 如何分层评测，哪些错误阻断发布？
7. 如何 trace，同时保护敏感数据？
8. 如何灰度、降级、回滚和人工接管？
9. 如何测量采用和业务影响？
10. 哪些现场经验应沉淀为产品能力？

能沿这十问稳定推理，比背诵任一框架或厂商产品更接近资深 AI FDE。
