# 从工作流出发做系统设计

> [!NOTE]
> **适合谁：** 系统设计容易变成组件清单，或者上线、权限和回退总在最后补的人<br>
> **首次通读：** 15 分钟；建议练习 45 分钟<br>
> **完成后产出：** 一张同时包含数据流、控制流和证据流的系统图

## 1. 系统设计不是云服务记忆比赛

FDE 系统设计的难点，是在需求不完整、数据复杂和上线压力下做一组有边界的决策。面试官通常不期待唯一架构，而是观察你是否：

- 先定义用户、流程和成功；
- 找出风险最高和最不可逆的边界；
- 让架构与规模、可靠性和组织能力匹配；
- 解释取舍，并知道什么证据会让你换方案；
- 把设计继续走到发布、观测、回滚和采用。

## 2. 45 分钟时间分配

一个可调整的节奏：

| 时间       | 目标                                         |
| ---------- | -------------------------------------------- |
| 0—7 分钟   | 用户、工作流、功能/非功能要求、规模、风险    |
| 7—12 分钟  | API、数据对象、成功与失败语义                |
| 12—25 分钟 | 高层数据流、控制流和关键状态                 |
| 25—35 分钟 | 两个最重要的深挖：权限、可靠性、检索、同步等 |
| 35—42 分钟 | 评测、观测、成本、发布和回退                 |
| 42—45 分钟 | 总结取舍、开放问题和下一步验证               |

如果面试官希望深入某个组件，主动重新分配时间。结构的作用是防止只画主路径后被迫结束。

## 3. 从 mission 开始

先用两三句话确认：

- 用户是谁，在哪个时刻使用；
- 当前最痛步骤是什么；
- 系统给建议、做决定还是执行动作；
- 什么指标改善，什么错误不可接受；
- 第一阶段规模和时间范围。

这一步会决定系统是搜索、助手、工作流还是 Agent，是同步还是异步，是强一致还是最终一致，是自动执行还是人工审批。

## 4. 同时画三条线

### 数据流

数据从哪里产生，如何摄取、规范化、版本化、存储、检索和返回。标出敏感数据和权限继承。

### 控制流

谁触发，系统怎样选择下一步，哪里重试，哪里审批，哪里终止或补偿。Agent 系统尤其不能只画模型调用。

### 证据流

每次结果如何追溯到输入、模型/提示版本、检索文档、工具调用和人工决定。没有证据流，评测、调试和审计只能靠猜。

## 5. 定义核心对象与状态

以支持助手为例，至少区分：

- `Conversation`：用户交互历史，不等于业务任务；
- `Task`：一个可追踪目标及其生命周期；
- `Document`：逻辑文档、版本、权限和删除状态；
- `ToolCall`：请求、参数、身份、幂等键、结果；
- `Approval`：谁在何时批准哪个版本的动作；
- `Trace`：请求链和决策证据；
- `EvalCase`：输入、期望、标签、版本和来源。

把所有东西塞进“chat session”会导致长任务恢复、审计和并发变得困难。

## 6. 容量估算要服务于决策

不需要追求虚假精确，但要问：

- 日活、峰值 QPS、并发和突发；
- 文档/事件量、平均大小、更新与删除频率；
- 模型和工具的延迟分布、速率限制；
- 数据保留时间和地域；
- 可接受的陈旧度、恢复时间和丢失量。

估算的目的是判断同步/异步、缓存、分区、批流、队列、索引和降级，而不是展示算术。

## 7. 可靠性设计

### 超时和重试

每个外部调用都需要超时。重试必须区分瞬时与永久错误，使用退避和抖动，并避免重试风暴。

### 幂等和副作用

模型可能重复提出动作，网络也可能让客户端不知道上次是否成功。写操作要有业务幂等键；不可逆动作需要审批或补偿。

### 降级

模型不可用时，是否回到搜索、模板、人工队列或只读模式？向量库不可用时，关键词检索是否足够安全？降级不能绕过权限。

### 隔离

按租户、客户、任务或资源池限制爆炸半径。一个大客户的长任务不能耗尽所有 worker。

### 恢复

状态必须独立于浏览器连接和单个 Pod。长任务需要 checkpoint、重放、取消、恢复和人工信号。

## 8. 权限和安全不是最后一层

设计时应尽早回答：

- 用户身份如何传递到数据与工具；
- RBAC、ABAC、租户和用途限制在哪里执行；
- 模型能看到哪些上下文，工具使用什么凭证；
- 是否使用用户委托身份，还是系统身份；
- 高风险动作是否需要 step-up auth 或审批；
- 日志、trace 和评测数据如何脱敏；
- MCP/connector/skill 的来源和版本如何信任；
- 撤销权限后，缓存和索引多久生效。

最重要的原则：**权限在获取上下文和执行动作之前强制执行，不依赖提示词。**

## 9. AI 层的设计问题

### 模型选择

按任务质量、结构化输出、工具能力、延迟、成本、数据边界和可用性选择。设计路由和 fallback 时要防止低能力模型承担高风险任务。

### RAG

摄取、解析、切分、权限、检索、重排、上下文组装、生成和引用验证需要分开观测。不要把“RAG 准确率”当成单一数字。

### Agent

明确目标、允许工具、状态、终止条件、最大步骤、预算、审批点和失败策略。对固定流程优先使用确定性编排。

### 上下文

系统指令、工具、示例、检索数据、消息历史和记忆都占预算，也都是攻击面。按需加载并记录来源。

### 评测

定义任务成功、安全、权限、工具正确性、引用、延迟、成本和业务结果。离线门禁与线上监控互补。

## 10. 发布不是设计后的附录

一个完整 rollout 可以分为：

1. 离线历史回放；
2. shadow 模式，不影响用户；
3. 内部或专家用户建议模式；
4. 小范围灰度，人工复核；
5. 低风险动作自动化；
6. 按指标和事故预算扩大；
7. 明确 rollback、kill switch 和客户支持。

每一阶段都应有进入、退出和暂停条件。模型分数好不等于可以扩大；用户绕过率或人工负担可能更早暴露问题。

## 11. 例题：设计多租户企业知识助手

### Mission

帮助支持人员快速找到最新政策并生成带来源的建议。第一阶段不自动执行客户账户动作。要求严格租户与角色隔离，政策更新 15 分钟内可见。

### 高层设计

```text
Source systems
  -> change capture / snapshot reconciliation
  -> canonical document + version + ACL
  -> parse / chunk / embed / index
  -> retrieval gateway (identity + tenant + ACL first)
  -> rerank / context assembly
  -> answer generation
  -> citation and policy validation
  -> UI suggestion + feedback

Across the path: trace, versions, evals, audit, freshness SLO
```

### 两个深挖

第一是同步与删除：稳定 `doc_id`、版本、tombstone、权限变化、失败隔离、回放和源目标对账。

第二是越权防护：身份传播、过滤前置、缓存分区、跨租户 canary、trace 脱敏、管理员文档和普通文档分级。

### 评测

分解为文档可用率、权限正确率、检索 recall@k、引用支持率、答案有用性、高风险错误率、首响时间和建议采纳率。权限违规是阻断指标，不能被平均质量分数抵消。

### 发布

先以搜索/建议模式上线一个团队，shadow 对比人工，逐步扩大知识域。任何跨租户命中、删除未传播或引用不支持都触发停止扩展。

## 12. 面试时如何表达取舍

不要只说“A 可扩展，B 简单”。完整取舍包括：

1. 当前决策目标；
2. 两个方案在关键约束上的差异；
3. 为什么当前阶段选择其中一个；
4. 这个选择的风险与补偿控制；
5. 哪个量化信号会触发迁移。

示例：

> 第一阶段我会用 Postgres + pgvector，减少运维面并让文档、版本、ACL 与向量在一致事务边界内管理。风险是规模和高级检索能力有限，所以我会监控索引大小、p95 延迟和召回；当单租户数据量或并发越过验证阈值，再迁移专用检索服务。迁移前保持 retrieval gateway 契约不变。

这比“先简单、以后扩展”更可执行。
