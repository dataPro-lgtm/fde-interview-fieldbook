# 开始之前：先把“准备面试”变成一个可交付项目

## 1. 你不是来读完这套资料的

FDE 的知识面很宽：代码、数据、系统、AI、产品、客户、上线、安全、沟通，任何一项都能单独学几个月。最危险的准备方式，是从第一页开始顺序阅读，觉得“看懂了”就等于“会回答了”。

这套 Fieldbook 的使用目标只有一个：把知识转成面试官可以观察到的行为。你最终应该拿出四类证据：

1. 能在十分钟内把一个模糊问题问清楚；
2. 能在白板上从工作流推导系统，而不是背架构；
3. 能讲透一个自己亲手交付的项目，包括失败和生产责任；
4. 能在追问中保持边界，不夸大、不乱承诺、知道何时需要更多证据。

## 2. 先确认你准备的是哪一类 FDE

岗位标题相同，工作重心可能完全不同。开始学习前，把目标职位描述贴进下面这张表，每一项只写职位原文能支持的证据。

| 维度     | 低权重信号         | 高权重信号                                                 |
| -------- | ------------------ | ---------------------------------------------------------- |
| 客户现场 | 偶尔支持客户       | embed、on-site、travel、own deployment                     |
| 编码     | technical guidance | hands-on keyboard、write production code、full-stack       |
| 数据     | 使用现成 API       | ingestion、distributed processing、data quality、pipelines |
| AI       | 一般 GenAI 经验    | agents、RAG、evals、MCP、skills、model behavior            |
| 行业     | 通用企业客户       | healthcare、government、GRC、finance、defense              |
| 产品化   | 完成项目           | reusable patterns、platform feedback、product roadmap      |
| 采用     | 部署成功           | adoption、workflow impact、enablement、knowledge transfer  |

完成后，用一句话描述目标岗位：

> 这是一个以 ______ 为技术主轴、以 ______ 为客户环境、要求从 ______ 负责到 ______ 的 FDE 岗位。

如果这句话写不出来，暂时不要开始刷题。你还没有定义自己的考试。

## 3. 做一次诚实的基线评估

打开[总评分表](../../interview-kits/rubrics/master-scorecard.md)，对八个维度各打 1—4 分。打分时只认最近两年能具体讲述或现场演示的证据：

- “学过 Kubernetes”不算交付证据；
- “知道 RAG 评测指标”不算设计过评测；
- “参与客户项目”不等于你做过客户发现；
- “团队把系统上线了”不等于你能说明自己的决策。

每个低分项再写两列：

| 差距               | 当前证据            | 7 天内可补的最小证据                           |
| ------------------ | ------------------- | ---------------------------------------------- |
| 例：不会讲采用     | 只讲过接口和准确率  | 重写一个项目故事，补用户、基线、采用障碍和结果 |
| 例：Agent 安全薄弱 | 只做过 tool calling | 完成一次工具权限、审批、幂等和审计的系统设计   |

你的训练 backlog 不应超过三个高优先级差距。FDE 看重广度，但面试失败通常来自一两个明显短板，而不是第十个知识点没背到。

## 4. 建立“证据账本”

准备一个表格，每一行只记录一个可以被追问的事实：

| 证据         | 情境                 | 你的动作                   | 决策依据             | 结果     | 反事实/复盘            |
| ------------ | -------------------- | -------------------------- | -------------------- | -------- | ---------------------- |
| 一次生产回滚 | 提示词升级后投诉升高 | 分桶 trace，回滚并补回归集 | 线上错误集中于某意图 | 恢复基线 | 以后先 shadow + canary |

一个成熟的项目故事，至少要能回答六类追问：

1. 为什么这个问题值得做？
2. 你如何确认根因而不是接受表面需求？
3. 哪些工作是你个人完成或主导的？
4. 你放弃了什么，为什么？
5. 如何证明结果，不只是“客户满意”？
6. 如果重做一次，会改什么？

没有真实经历时，可以用公开或自拟案例练习判断，但必须明确说“这是设计练习”。不要把练习包装成客户项目。

## 5. 每次练习都要留下可复盘产物

建议使用下面的训练闭环：

```text
第一次回答（限时）
  -> 用评分表自评
  -> 只找最大的两个问题
  -> 针对性补知识或重构结构
  -> 第二次回答（录像）
  -> 找同伴盲评
  -> 记录一个可复用规则
```

不要在一次复盘中修改十个问题。先处理会让面试官停止相信你的问题，例如：没有澄清就上架构、虚构指标、把所有流程 Agent 化、无法区分个人贡献、没有权限或回退方案。

## 6. 推荐学习顺序

### 软件工程师转 FDE

先读[岗位地图](01-role-map.md)、[客户发现](03-discovery.md)和[行为面](09-behavioral.md)，再读生产 AI。你的短板往往不是技术深度，而是业务问题、采用和客户语言。

### 数据工程师转 AI FDE

先读[生产 AI](06-production-ai.md)和[系统设计](05-system-design.md)，把数据质量、幂等、血缘和回放优势连接到 RAG/Agent 可靠性；再补[客户发现](03-discovery.md)。

### 解决方案架构师/售前转 FDE

先读[编码、数据与交付](04-coding-data-delivery.md)，准备能证明亲手实现和调试的材料；然后用[案例册](07-casebook.md)训练从白板走到验收和事故。

### AI 应用工程师转 FDE

先读[岗位地图](01-role-map.md)和[客户发现](03-discovery.md)。你需要证明的不只是 Agent 能运行，而是选择它的理由、风险控制、采用和可维护性。

## 7. 准备完成的定义

当你能够稳定做到以下事项，才算进入面试状态：

- 90 秒自我介绍同时讲清技术主轴、客户价值和生产责任；
- 五分钟内画出当前工作流，而不是先画目标系统；
- 现场写出可读、可测、能解释复杂度的代码；
- 用一条请求链解释数据、权限、模型、工具和观测点；
- 对一个不合理客户要求给出有替代方案的拒绝；
- 对一次失败说清影响、判断、动作、结果和机制改进；
- 任何公司流程信息都能区分“官方确认”和“社区经验”。
