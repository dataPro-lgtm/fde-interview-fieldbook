# Start here

This fieldbook is not meant to be read cover to cover before you practise. Use it to produce interview evidence.

## 1. Identify the role you are actually targeting

FDE titles cover different jobs. Extract evidence from the current job description:

| Dimension         | Questions to answer                                                             |
| ----------------- | ------------------------------------------------------------------------------- |
| Customer exposure | Are you embedded, on-site, travelling, or supporting remotely?                  |
| Engineering       | Is the role hands-on full-stack, data-heavy, infrastructure-heavy, or advisory? |
| AI                | Does it name RAG, agents, evals, MCP, skills, or model behaviour?               |
| Industry          | Is domain learning or regulated delivery central?                               |
| Adoption          | Does success include usage, workflow impact, enablement, or handoff?            |
| Product feedback  | Are reusable patterns and roadmap input explicit outputs?                       |

Write one sentence:

> This is a ______-centred FDE role in ______ customer environments, owning the path from ______ to ______.

If you cannot fill that sentence, do not start with a generic question bank.

## 2. Run a baseline

Use the [master scorecard](../../interview-kits/rubrics/master-scorecard.md). Score only evidence you can explain or demonstrate:

- customer discovery and decomposition;
- value, product judgement, and adoption;
- coding, debugging, and end-to-end delivery;
- data engineering and system design;
- AI application engineering;
- evaluation, reliability, observability, and cost;
- security, permissions, and governance;
- communication, handoff, and productization.

Any score of 1 is a potential rejection risk. Choose no more than three priorities.

## 3. Build an evidence ledger

For each strong project or incident, record:

```text
Context and baseline
Your exact ownership
Decision and evidence
Trade-off and rejected alternative
Measured result
What failed or remained unresolved
Mechanism changed afterwards
```

If the work is a practice case rather than a real deployment, say so. Credibility matters more than scale.

## 4. Use the FIELD loop

```text
Frame the mission
Inspect reality
Engineer the thin slice
Launch and learn
Distill into product
```

The loop applies to customer cases, system design, project stories, and incident follow-up. It prevents a common failure: choosing architecture before understanding the workflow.

## 5. Practise through artifacts

A useful session produces one of:

- a ten-minute discovery recording;
- a one-page mission memo;
- tested code and an error log;
- a system design with data, control, and evidence flows;
- a scored mock interview;
- a rewritten project story with measurable outcomes.

Reading without retrieval practice creates familiarity, not interview performance.

## 6. Ready-state checklist

You are ready when you can consistently:

- explain your fit in 90 seconds;
- map the current workflow before proposing a solution;
- code and test under the target format;
- follow one request through data, permissions, models, tools, and telemetry;
- decline an unsafe ask while offering a practical alternative;
- explain one failure without blame or false certainty;
- distinguish official hiring evidence from community reports.
